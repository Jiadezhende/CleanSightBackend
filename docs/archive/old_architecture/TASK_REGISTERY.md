# Task Registery

随着模型逐步复杂，每个清洗阶段至少会有2个模型参与推理（追踪+分类），且不同阶段有不同组合。因此不适合静态地在TaskRegistry中设置每个阶段所用的模型组合。

## 多模型推理调度优化方案

### 概述

本项目重点在于实时性，针对一个节点处理多个客户端推理任务的场景，设计公平调度和模型间消息传递机制，确保延迟可控（目标<300ms）。方案结合Round-Robin/Weighted Fair Queuing (WFQ)调度、异步队列和流式传递，实现低延迟高吞吐。

### 1. 公平调度算法

- **算法选择**：优先使用WFQ，为实时客户端分配更高权重（e.g., 监控任务权重=3），确保优先执行。RR作为备用。
- **实现步骤**：
  1. 每个客户端维护独立FIFO队列。
  2. 调度器轮询队列，计算虚拟完成时间（VFT）选择任务。
  3. 分配到GPU/CPU资源执行，时间片200-300ms。
- **实时约束**：硬阈值100ms触发优先调度，限制并发任务数（e.g., 4个），监控P95延迟>阈值时降级。
- **优势**：避免垄断，确保公平。

### 2. 模型间消息传递

- **架构**：使用内存队列（asyncio.Queue）进行Pub/Sub传递，避免网络延迟。
- **追踪阶段**：每帧独立（~30帧），输出坐标列表，发布消息`{"frame_id": int, "coordinates": list, "client_id": str}`。
- **动作分析阶段**：需15帧，维护滑动窗口缓冲区。收到帧后更新缓冲，支持部分帧（e.g., 10帧）开始推理。
- **传递流程**：
  1. 追踪发布消息到队列。
  2. 动作分析监听，聚合多帧触发推理。
  3. 异步非阻塞，流式处理减少等待。
- **容错**：超时重发，帧丢弃策略。

### 3. 实时性优化

- **调度调整**：短时间片、权重动态调整、并发限制。
- **传递优化**：内存队列、滑动窗口、模型预热、小批量推理。
- **整体保障**：边缘计算、端到端延迟<300ms、吞吐>50 FPS。使用Locust测试。
- **实现优先级**：先优化追踪，再完善动作分析。

此方案可集成到TaskRegistry的动态组合中，逐步实现。
