# 后台页面重做：以 run 为中心的统一控制台，五个功能收进四页一个工作台

> **变更状态**：提案（2026-10-25）——页面划分与交互待人确认；后端补口与技术栈三项决策待定
> **知识库**：无需沉淀（提案本身；结论随各批记录沉淀）

## 概述

新建一个控制台 `/ui-f3m8/console/` 替换 admin 和 lab 两个页面，按 run 组织：总览 → 选 run → **Run 工作台**。
双轨回放是工作台的播放器底座，复核送标与离线分析是工作台右侧的两个面板，共用同一条多泳道时间轴。
实时监控、分析作业队列、系统运维各占一页。前端不写业务字段，以后端为准；为此后端补五处读口（playlist 逐段墙钟时间、step 能力表、任务清单只列有录像的任务、送标上限、断流点）。新旧页面并存，五批迁完后删除旧页面。

可点击的交互样例（前端假数据，不连后端）：[docs/design/console_mockup.html](../design/console_mockup.html)，浏览器直接打开。

## 变更背景

- **现状**：
  - 共两个页面：admin 有 6 个 tab，lab 是一个单页工作台。录像在三处分别播放：admin 离线 tab、lab，以及历史回放（目前没有页面，只有接口）。
  - 三处各有一套选任务方式：手动输入 id、任务表、作业表，相互之间不联动。
  - 告警有三种来源（实时内存、`clean_alarm` 表、离线 `alarms.jsonl`），字段名和时间单位各不相同，三处分别渲染。
- **痛点**：

| # | 问题 | 影响 |
|---|------|------|
| 1 | **双轨只是切换查看，不能对照**；切轨时按相同秒数续播，而两轨媒体轴的原点不同（processed 晚起） | 切到 processed 后落在错误的时刻，复核时容易对错帧 |
| 2 | 回放、离线分析、送标是三个孤立页面，告警没有画在时间轴上 | 复核一条告警要在两个页面之间手动对照时刻 |
| 3 | 所有请求都不带 `run_id` | step 重启后，录像、打点、送标可能来自不同 run，而且不会报错 |
| 4 | 断流位置不可见，只显示一句「含信号中断」 | 送标时裁到断流处，提交后才报 `range_gap` |
| 5 | 选中任务后还要再点一次「加载」；切换任务会直接清空已选片段；部分失败后重新提交会重复上传已成功的段 | 操作多，容易丢工作 |
| 6 | 7 处轮询的错误都被 `catch {}` 吞掉 | 后端挂了时页面只是不再刷新 |
| 7 | 页面状态不写进 URL | 刷新后丢失状态，链接也无法分享 |
| 8 | `/task/history`、`/task/live`、`/health/monitor/*` 等接口已有，但没有页面使用 | 历史任务没有回放入口 |

- **约束（已定，不再讨论）**：
  - 回放复核只在后台使用，不接入业务平台。
  - 以离线判定为主；CLEAN 在线叠字不投入；实时告警属过渡方案。
  - 一次 run 就是一次完整流程，默认看最新 run。
  - 离线盘上告警属过渡方案，相关代码要控制耦合面。
  - 生产环境离线部署，前端依赖放在 `app/static/vendor/`。

### 1. 任务总览 `#/tasks`

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│ [在线 2 | 全部]  搜索 task_id / 点位 IP ________        只列有录像的任务 · 共 N 条 │
├──────┬───────────┬──────────┬──────────────────────────────────┬───────────┤
│ task │ 点位 IP    │ 状态      │ steps（芯片：别名 / 离线态）        │ 更新时间    │
│ 128  │ 10.0.0.12 │ ● 运行中  │ [1 LEAK ●直播]                      │ 10-25 …   │
│ 127  │ 10.0.0.11 │ 已完成    │ [1 LEAK] [2 CLEAN ✓28 ⚠3]           │ 10-24 …   │
└──────┴───────────┴──────────┴──────────────────────────────────┴───────────┘
```

- **只列有录像的任务**：没有任何录像段的任务不出现；有录像的任务里，没有录像的 step 也不出芯片。刚开跑、首段还没落盘的任务，等首段落盘（秒级）后出现。
- **筛选只有两档**：「在线」与「全部」，加一个搜索框。不做「最近完成」，也不做离线结果过滤——后期所有任务结束都会跑离线推理。
- **数据来源**：
  - 「在线」：`/admin-f3m8/overview`，3s 轮询。
  - 「全部」：`/lab-f3m8/tasks`，分页并带 `q`；以磁盘上有录像的任务为准、平台库过滤并补字段，需要后端配合（§8 B3），前端过滤会和分页冲突。
  - 响应 `source` 为 `storage` 时（平台库连不上已退回，或配置为仅磁盘），工具栏挂一条提示，IP / 状态列显示「—」。
- **step 芯片是唯一操作入口**：
  - 点芯片直接进入该 step 最新 run 的工作台；直播中的 step 进实时监控。
  - 芯片显示：别名、离线状态（未跑 / 排队 / 运行 / 失败 / 完成带段数和违规数）；没有离线模型的 step 不显示离线状态。不显示录像轨：缺 processed 轨只影响工作台里的并排对照，由工作台自己置灰提示。
  - 别名和「是否有离线模型」来自 step 能力表（§8 B2）。

### 2. Run 工作台：双轨播放器 + 多泳道时间轴

```text
┌ 任务 128 · step 2 CLEAN · run 2026-10-24 14:03:11 · 时长 12:40 · 断流 2 处 38s [raw|processed|并排] ⬇下载▾┐
│ ┌──────────── raw（主）────────────┐ ┌───────── processed（跟随）─────────┐ │ 面板 [事件][离线][送标] │
│ │                                  │ │   （尚无画面：推理预热中）           │ │                         │
│ └──────────────────────────────────┘ └────────────────────────────────────┘ │  见 §3 / §4             │
│  ▶ 03:12.400 / 12:40   🕒 14:06:46.800   1x ▾                    [适应全程]  │                         │
│ ─────────────────────────────────────────────────────────────────────────── │                         │
│ 刻度   02:50   03:00 [断流 23s]   03:10   03:20 …                            │                         │
│ 事件        ▼              ◆ ▼                          整段违规 ×1          │                         │
│ 分割段 ▇idle▇▇insert▇▇withdraw▇▇idle▇▇flush▇▇▇insert▇▇…                     │                         │
│ 概率 ▸（默认折叠，点开看逐帧曲线）                                             │                         │
│ 送标片段    [====]          [==]                                             │                         │
│        ▲ 播放头；滚轮缩放、拖动平移、在送标片段上拖选/拖边                       │                         │
└──────────────────────────────────────────────────────────────────────────────┴─────────────────────────┘
```

- **双轨对时**：
  - raw 是主轨，processed 跟随主轨，换算链为 raw 媒体 ms → 墙钟 → processed 媒体 ms，逐段对照表来自两轨 playlist 的 `PROGRAM-DATE-TIME`（§8 B1）。
  - 播放时持续校正：偏差超过 150ms 时 seek，偏差较小时微调 `playbackRate` 追平。
  - 主轨的时刻落在 processed 没有画面的区间（首段预热、断流）时，processed 显示遮罩「此刻无标注画面」，不跳走。
- **单轨模式**：只保留一个 `<video>`，在两轨之间切换时按墙钟换算位置，修复痛点 #1 的切轨错位。
- **时间轴泳道**（只留 4 条 + 刻度尺）：
  - 所有泳道共用 raw 媒体坐标和同一个缩放窗口，改为自绘 canvas。原因是 Chart.js 两张图靠固定 72px y 轴宽度对齐，泳道一多就对不齐。
  - 断流：断流在 raw 媒体轴上宽度为零（播放器把前后两段首尾接上），所以画在刻度尺上（红色标签注明断了多久），并拉一条贯穿各泳道的红线，不单占一条泳道。断流点由后端给（timeline 的 `gaps[]`，§8 B5），前端不复刻 `GAP_THRESHOLD_MS` 判据。送标前就能看到断点（痛点 #4）。
  - 事件：平台告警（▼）与离线违规（◆）合一条泳道，整段判定的违规在泳道右端计数。
  - 概率默认折叠，点泳道名展开。
  - 某条泳道没有数据时显示该泳道自己的空状态，例如「未跑离线推理」「LEAK 无离线模型」。
- **快捷键只留两个**：空格 播放/暂停，←/→ 前后 1 秒。其余操作都有可见入口。
- **精简掉的**：倍速只留 1×/2×/4×；不显示对时偏差和视窗范围；不做缩略条和缩放按钮（滚轮缩放 + 「适应全程」）；只有一个 run 时不显示 run 下拉。
- **下载**：一个「下载 ▾」菜单选 raw / processed。先用 `HEAD` 预检，再给出 loading 状态和可读的错误提示，取代裸 `<a download>`。

### 3. 复核送标面板

**事件**（`?panel=review`）：

```text
◆ 03:15.0  warning STEP_DURATION 灌注时长 45.0s，低于要求 60s       离线违规   ← 有时刻 → 点击 seek
◆ 10:50.0  warning STEP_MISSING  第 6 次插刷后缺少抽刷             离线违规
▼ 12:25.0  medium  任务超时      step 运行已超过 12 分钟           平台告警   ← clean_alarm
◆ 整段      warning STEP_COUNT    插刷—抽刷配对 5 次，要求 ≥ 6 次   离线违规   ← 无时刻，不可跳
                                    [生成前后 5 秒的送标片段]   ← 选中有时刻的事件才出现
```

- 两种来源经适配层（§7）归一成同一种行，按时刻排序，不做来源 / 级别筛选。类型、级别、文案都原样显示后端的值：平台告警取 `alarm_type` / `severity` / `message`，离线违规取 `metric` / `alarm_level` / `alarm_message`。
- 「生成前后 5 秒的送标片段」：以事件时刻为中心，碰到断流就在断点处截短，直接加入送标片段。

**送标**（`?panel=label`）：

```text
LS ● 可达                       project [12]        ← 默认值取 LS 配置的 default_project_id，可手填
送标片段                         2/20 · 22s/30m00s    ← 上限取自后端（B4）
┌ # 区间             时长  状态                ┐
│ 1 01:07.0–01:17.0  10s  ✓ LS#5521   已锁定 │  ← 行可点 seek；拖时间轴上片段边缘即改
│ 2 02:56.0–03:08.0  12s  ✗ 失败          ✕  │
│   <后端 error 原文>  按断点拆分                │  ← 原样显示 /submit 的 error + 一键修正
└────────────────────────────────────────────┘
                  [提交未成功的 1 段]
```

- **打点只有一种方式**：在时间轴「送标片段」上拖选，松手即加入（不足 1 秒视为误触忽略；超过单段上限截断、段数上限拒绝，上限取自后端 B4；重叠拒绝并提示）；拖片段边缘微调。不再有「设起点 / 设终点 / 加入」三步和对应快捷键。
  - 只能在 raw 轴上打点：并排模式下 processed 窗口只供参考，单轨 processed 模式下禁用打点。
- **丢工作保护**：有未提交片段时，离开当前 run（换 run、刷新、关闭页面）要先确认；片段按 run 暂存在 `sessionStorage`，回到同一 run 时恢复。
- **提交**：
  - 只提交未成功的段，已成功的段锁定并显示 LS task 链接，修复部分失败后重传导致 LS 出现重复任务的问题。
  - 后端是同步执行，前端只能显示整体 loading 加已等待秒数。
- LS 健康检查改为异步，不再阻塞加载录像。

### 4. 离线推理：工作台面板 + 队列页

**工作台「离线分析」面板**（`?panel=offline`）：

```text
状态 ✓ 已完成 10-24 15:20 · 耗时 42s     结果 28 段 · 违规 3 条
[重跑离线推理]                          ← 本 run 在跑时禁用并显示进度
动作类别（点击高亮）  ■idle ×11 ■air_injection ×3 ■flush ×3 ■long_brush_insert ×6 ■long_brush_withdraw ×5
                      ← 类别与顺序取 label-probs 的 labels[]，名字原样显示
```

- 提交作业时带当前 `run_id`。作业跑完后，只要还停留在这个 run，就自动刷新分割、概率、违规三条泳道，不再要求「提交前已加载」。
- 结果库提案落地后，可以在这里增加「版本」下拉（按 `result_id` 选版本，默认最新），本提案不依赖它。

**分析作业页** `#/offline`（侧栏「分析」）：

```text
[全部 | 运行中 1 | 排队 3 | 已完成 | 失败]
┌ task │ step │ run          │ 状态     │ 模型      │ 段 │ 违规 │ 耗时 │ 提交       │ 说明 ┐
│ 128  │ 2    │ 10-24 14:03  │ ● 运行中 │ MSTCN2…   │ —  │ —    │ 0:31 │ 15:19:40  │      │ → 行点击进工作台离线面板
```

- 只看队列与历史，不在这里提交。去掉手动输入 task_id / step_id，也不做「待跑候选」批量提交——后期所有任务结束都会自动跑离线推理，过渡期手动入口只有工作台「离线分析」面板。
- 「刚跑完」的作业在列表里高亮几秒，并弹 toast，toast 带「查看结果」链接。

### 5. 实时监控 `#/live/{task}?`

```text
┌ 在线 run ───────────┐┌──────────────── task 128 · step 1 LEAK · 10.0.0.12 ────────────────┐
│● 128 LEAK 10.0.0.12 ││                                                                    │
│  BUBBLE● BENDING○    ││                  WS 推理画面（task_id 模式锁定 run）                 │
│  告警 3              ││                                                                    │
│○ 129 CLEAN 10.0.0.13 │└──── 12.3 fps · 末帧 0.2s 前 · ● 直播 ───────────────────────────────┘
│  无实时信号           │ 信号(10s)  BUBBLE ● 命中 7 max 0.83   BENDING ○
└──────────────────────┘ 告警流  14:05:22 high 气泡持续 …   [回放此刻]
                         [打开回放工作台]
```

- **左侧 run 列表**：
  - 每路显示信号灯（按 1Hz 拉 `/task/message` 的 `signals_10s`）和告警数。不放队列积压：它是运维指标，没有刻度和阈值的迷你曲线也读不出结论，放到系统运维看当前值。
  - 只有右侧聚焦的那一路连 WS，因为每帧约 55KB，不做多路画面墙。
- **WS 连接方式**：改用 `task_id` 模式。聚焦的 run 结束时收到 `idle`，页面提示「run 已结束」并给出「打开回放」按钮。
  - 原来的 `client_id` 跟随模式会悄悄切到同点位的新 run，而 `since_seq` 不重置，告警会串号。
- **卡顿判断**：末帧超过 3s 未更新就显示「画面停滞」，因为 WS 没有心跳。
- **告警流**：每行带「回放此刻」，打开该 run 的工作台并定位到该时刻。运行中的 run 的 playlist 会偏短，定位不到时贴到尾部并提示。

### 6. 系统运维 `#/system`

- **六块内容**：

### 7. 外壳、路由与适配层

```text
app/static/console/
  index.html                 外壳：侧栏 + 顶栏 + <router-view>
  app.js                     hash 路由（自写 ~60 行，不新增依赖）、全局健康灯
  api/                       唯一出网层：fetch 封装（错误进健康灯/toast）+ 各 router 的读写函数
    adapters.js              三类告警 → AlarmRow{source, level, metric, message, wall_ms?, media_ms?}；
                             秒/毫秒字段在此统一成 ms，页面只见 ms
  components/
    DualPlayer.js            双轨播放器 + 对时
    TimelineLanes.js         多泳道 canvas 时间轴（缩放/平移/拖选）
    StepChip.js / LevelTag.js / RunHeader.js
  pages/  tasks.js · run.js · live.js · offline.js · system.js
```

- 页面不直接调 `fetch`，统一走 `api/`。
- 离线盘上告警端点只在 `adapters.js` 里出现一次。告警入库后只需改这一处，改为读 `/task/{id}/alarms`，泳道和面板代码不动。
- 所有可分享的状态都进 URL：task / step / run / panel / 时刻 `t=`。刷新页面或转发链接都能回到同一画面。
- **前端不写业务字段，以后端为准**：

  | 内容 | 来源 |
  |------|------|
  | step 别名、是否有离线模型 | B2 `/admin-f3m8/stages` |
  | 动作类别及其顺序 | `/lab-f3m8/label-probs` 的 `labels[]`；分割段的 `label` 原值 |
  | 告警 / 违规的类型、级别、文案 | `clean_alarm` 原值；离线 `metric` / `alarm_level` / `alarm_message` |
  | 实时信号指标 | `/task/message` 的 `signals_10s` 键 |
  | 任务状态 | `clean_task.status` 原值；是否在线看 overview |
  | 送标失败原因 | `/submit` 每段的 `error` |
  | 送标上限 | B4 |
  | 断流点 | B5 |
  | LS 地址、默认 project | `/lab-f3m8/config` |
  | 模型名、指标名 | 作业的 `model`、`/metrics/json` 的键 |

  前端只保留与业务无关的展示规则：级别 → 颜色（未知值灰色），类别按后端顺序从调色板取色。文字一律原样显示，不做中文翻译表。
- **视觉**：
  - 全站浅色，回放工作台也一样；只有视频画面本身保留黑底。
  - 级别配色全站一套（critical/high 红、medium 橙、low/warning 黄、其余灰）。
  - 类别颜色按后端 `labels[]` 顺序取调色板，分割泳道、概率曲线、图例共用。
  - 数字用等宽字体。

### 8. 后端补口（五处，都是读口）

| 编号 | 内容 | 消费方 | 必要性 |
|------|------|--------|--------|
| B1 | `/traceback/.../playlist.m3u8` 每段前加 `#EXT-X-PROGRAM-DATE-TIME`（该段墙钟起点 `s.ref.ts_ms`）；前端从 hls.js 解析出的 fragment 读 `programDateTime` / `start` / `duration` 得到逐段墙钟↔播放轴对照表。`render_vod` 的 `VodEntry` 加可选墙钟字段，只有浏览器清单填，喂 ffmpeg 的清单不变；timeline 不改 | 双轨对时、单轨切换保位 | 双轨回放的前提 |
| B2 | `GET /admin-f3m8/stages` → `[{step_id, alias, has_offline_model, has_compliance}]`，读推理配置 | 总览芯片别名与离线状态、工作台空状态文案 | 不做就要在前端硬编码别名和能力，配置一改就失配；目前只能靠提交后返回 400 才知道不可离线 |
| B3 | `/lab-f3m8/tasks` 的 `task_source=db` 改为「磁盘 + 平台库」：先按盘枚举有录像的任务（storage 模式现有逻辑），再用平台库过滤一遍（库里没有的不列）并补 IP / 状态 / 更新时间，然后分页，`total` 按过滤后计；平台库连不上时自动退回 storage 的结果。响应加 `source: "db" \| "storage"` 标明本次实际来源。`task_source=storage` 不变 | 总览「全部」、运维页「当前生效」 | 现在 db 模式按 `clean_task` 分页，会带出没有录像的任务，前端过滤会让分页和总数对不上（旧 admin 离线 tab 就是这个问题）；平台库挂了直接 503，要人手动切到 storage |
| B4 | `GET /lab-f3m8/config` 增 `limits: {max_clips, max_clip_ms, max_total_ms}`，取 settings 的 `lab_export_max_clips_per_submit` / `lab_export_max_clip_ms` / `lab_export_max_total_ms` | 送标面板的计数、截断与提交前校验 | 旧 lab 页把 20 / 5min / 30min 写死在前端，要和后端手动同步 |
| B5 | `/traceback/.../timeline` 增 `gaps: [{media_ms, wall_from_ms, wall_to_ms}]`（按轨，用 `media_timeline` 现有的 `GAP_THRESHOLD_MS` 判据，与送标报 `range_gap` 同源） | 刻度尺断流标记、事件前后 5 秒片段避开断点、片段跨断流提示 | 不做就要在前端复刻 500ms 阈值，阈值一改前端提示与后端报错就不一致 |

- 其余全部复用现有端点。B3 改变 `/lab-f3m8/tasks` 在 db 模式下的返回集合与错误行为（503 → 退回 storage），需同步 `docs/api/lab.md`；lab 旧页面在第 3 批前仍用它，只会少掉本来就无法送标的任务。
- 可选：离线作业取消端点（服务里已有 `cancel()`），放到 §4 队列页，优先级低。

## 遗留风险 / 后续任务

| 风险 / 待办 | 影响 | 处理计划 |
|------------|------|---------|
| 类别名、规则 `metric` 原样显示英文（如 `long_brush_insert`、`STEP_MISSING`） | 可读性一般 | 需要中文名时由后端在 B2 / label-probs 里加 display name，前端不建翻译表 |
| processed 实测成帧率波动 | 并排播放时 processed 画面可能一顿一顿，但时刻是对的 | 对时校正只保证时刻对齐，不追求流畅度 |
| `/submit` 同步执行，长批次可能等待数十秒 | 送标时只能显示整体 loading | 维持现状；以后需要再改为作业化 |
| 结果库提案批 2 可能把作业时间字段从秒改为 ms | 离线页的时间显示 | 只改适配层一处 |
| 离线告警入库后端点删除 | 违规泳道的数据源 | 只改适配层一处（§7） |
| processed 帧盖的是被推理帧的 ts，底图却是渲染时刻的最新 raw 帧（`visualization_worker.py`，KB 记为有意设计） | 按 ts 对齐后，processed 的框与同屏 raw 画面对得上，但 processed 底图比 raw 超前一个推理延迟（未测量，积压时更大） | 播放器无法补偿；并排模式标注「processed 底图超前约一个推理延迟，以框对照 raw 画面」 |
| 帧 ts 是 decoder 读到帧时的 `time.time()`，无 NTP 跳变防护 | 时钟跳变会制造假断流或段序错乱；回放、送标、告警落点已依赖同一假设，对时不引入新风险 | 不在本提案处理 |
