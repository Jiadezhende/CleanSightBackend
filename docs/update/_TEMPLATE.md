# 变更记录填写模板

> 复制本文件正文（从下方 `---` 之后）另存为新变更记录。本说明部分不要保留。

**命名**：变更记录统一放在 `docs/update/`，按 `日期_大写关键词.md` 命名，例如 `20260616_DOWNGRADE_TO_YOLO.md`、`20260613_ENV_ISOLATE.md`。

**篇幅自适应**：小改动只需保留「标题 + 状态块 + 概述」三段即可；涉及多文件/配置/回退的改造再按需补全「改动详情 / 数据通道 / 恢复方式 / 验证」等小节，没用到的整段删除，不要留空壳。

**别搞「总纲 + 引用」**：每篇变更记录是**能独立读完的任务单元**，把自己的契约/前提/背景写进本文，不要把它甩给一篇「总纲/hub」文档、让读者非跳过去不可（`契约前置：X`、`取自定稿见 X`、正文靠 `见 X §Y` 才成立，都属此病）。任务确实可能依赖之前的重构——那就用一句话点明依赖关系（「本次建立在 XX 换键之上」），但不把关键内容留在别处。可正常链接**代码**（`../../app/...`）、**对外 API/wire 文档**、**知识库**（`../kb/...`）——这些是真源，不是平级变更记录。

**两条状态轴（务必都填）**：

- **变更状态** = 这次改动的技术生命周期，决定它该不该进知识库。`已回退` 不仅不沉淀，还应触发清理 kb 里对应的旧结论。
- **知识库** = 这条记录有没有被聚合进 `docs/kb/`。新写的记录默认 `待沉淀`；定期维护时把已生效内容沉淀进 kb，再回填 `已沉淀 → 目标kb文件(日期)`，此后该记录变为纯历史，聚合自动跳过。

定期聚合时，先用一行命令捞出欠债：

```bash
grep -l '待沉淀' docs/update/*.md          # 列出所有尚未进 kb 的变更记录
```

仅把「变更状态 = 生效中」的内容写入 kb；遇到 `已回退`，反向检查并删除 kb 中失效结论。沉淀后务必更新目标 kb 文件顶部的「更新时间」（见 [kb/KB_MAINTENANCE.md](../kb/KB_MAINTENANCE.md)）。

`````markdown
# {改造内容核心，一句话点题}

> **变更状态**：生效中（YYYY-MM-DD）　<!-- 生效中 / 进行中 / 已回退 / 提案；一句话说明当前系统实际处于什么状态 -->
> **知识库**：待沉淀　<!-- 待沉淀 / 已沉淀 → [目标kb文件](../kb/XXX.md)(YYYY-MM-DD) / 无需沉淀(临时性变更，原因) -->

> 承接：一句话点明依赖的前序重构（若有），不跳转别处取关键内容。

## 概述

用 2~4 句话讲清楚：

- **改了什么**：这次变更的核心动作。
- **为什么改**：触发原因（需求 / 评审阻断项 / 线上问题 / 重构）。
- **影响面**：哪些模块、配置、接口或行为发生变化。

> 阻断项 / 风险较多时，可用表格列出：
>
> | 编号 | 问题 | 风险 |
> |------|------|------|
> | #1 | …… | 上线阻断 / 高 / 潜在正确性 |

## 改动详情

> 每个改动点一个小节，标注**文件路径**，必要时给出「旧 → 新」对照。可点击的代码引用用 [`符号名`](../../app/path/file.py) 形式。

### 1. `path/to/file` — 一句话说明改动意图

#### 旧
```
…变更前关键片段…
```

#### 新
```
…变更后关键片段…
```

> 关键决策 / 约定统一 / 易踩坑点用引用块补充说明。

### 2. 保留项（不改动）

- 明确列出**刻意保留**的代码/配置，避免后人误删或误以为遗漏。

## 数据通道 / 行为说明（可选）

> 当改动影响数据流向、队列、开关语义时，用表格澄清「谁写、谁读、本次开关是否影响」，消除误解。

| 通道 | 填充 | 消费 | 本次影响 |
|------|------|------|---------|
| …… | …… | …… | 是 / 否 |

## 如何恢复 / 后续计划（可选）

> 回退类或分期落地的改动，列出复原步骤或下一期待办；尤其标注「恢复前必须先修的阻断项」。

1. ……
2. ……

| 相关单测 | N passed |
| 配置加载 / 启动自检 | …… |
`````
