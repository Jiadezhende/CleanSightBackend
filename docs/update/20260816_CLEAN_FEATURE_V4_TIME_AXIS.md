# CLEAN 特征 v3 → v4：删掉时间位置编码，修正 fps 估计（71 → 68 维）

> **变更状态**：已落地（2026-08-16）　**知识库**：待沉淀
> **契约影响**：`FEATURE_VERSION` 由 `clean_bbox_v3_detectable` 改为 `clean_bbox_v4_notime`。三个存量 checkpoint 全部作废——`feature_names` 门禁会在加载时抛错，训练仓需按新特征重训。

## 一句话

`t_norm/t_sin/t_cos` 三列删除（伪时序信号），`effective_fps` 由中位数改均值（消除 7.5~12.9% 系统偏差）。维数 71/73/151 → **68/70/148**。

## 起因

问「离线推理的 ts 特征有没有归一化」，翻出 [bbox.py](../../app/services/inference/offline/blocks/bbox.py) 末尾三列：

```python
t = np.linspace(0.0, 1.0, frames)
[t, sin(2πt), cos(2πt)]  → t_norm / t_sin / t_cos
```

问题不在"归没归一化"，在**它一个 ts 都没读**：三列全是帧序号的确定性函数，一个自由度占三维；`t_norm` 更是「整段进度百分比」——算它必须先知道总帧数（因果链路根本算不出），且把 step 时长归一了，2 分钟和 10 分钟的段里同一个 `0.5` 相差 4 倍绝对时间。模型能学到的只有「训练集里这动作一般出现在第百分之几」。

## 测了什么

本地两条真实 step：`1785995202505/2`（1886 帧 / 125.7s）、`99/2`（428 帧 / 28.5s）。

| 观测 | 1785995202505/2 | 99/2 |
|---|---|---|
| dt 分位 p1/p50/p99 | 11 / 72 / 118 ms | 23 / 75 / 102 ms |
| 相邻 dt 自相关 lag-1 | **−0.478** | **−0.505** |
| `corr(\|Δcoord\|, dt)` | −0.026 | −0.138 |
| `effective_fps` 中位数法 vs 真值 | 13.957 vs 14.998（**−7.5%**） | 13.278 vs 14.987（**−12.9%**） |
| 帧轴累计漂移（中位数法定 fps） | −9.37 s ≈ 131 帧 | −3.67 s ≈ 49 帧 |
| 帧轴累计漂移（均值法定 fps） | **max 72.5 ms，末端 0** | **max 59.9 ms，末端 0** |

## 结论：抖动是时间戳噪声，不是真实采样间隔

dt 看着抖得厉害（11~132 ms，10 倍跨度），但三个互相独立的证据指向同一个模型 `dt = T + e_i − e_{i−1}`（真实间隔 T 恒定，时间戳叠 i.i.d. 噪声 e）：

1. **自相关 −0.478 / −0.505 ≈ 理论值 −0.5**。该模型下 `corr(dt_i, dt_{i+1}) = −Var(e)/2Var(e) = −0.5`，这是它的指纹。
2. **`corr(|Δcoord|, dt) ≈ 0`**。若 dt 是真实间隔，两帧间的位移应随 dt 增长；实测无关，甚至 `99/2` 里短 dt 对应的位移反而更大。
3. **均值法定 fps 后漂移不再累积**，恒在 1 帧以内（72 ms）、末端归零——噪声在求和时相消，正是该模型的推论。

真实采样率是稳的 **15.0 fps**。推出的 `std(e) ≈ 15~17 ms`。

## 因此，两条"显而易见"的改法都是错的

落地过程中先按直觉实现了这两条，被上面的数据否掉，已回退：

| 曾以为 | 实测 | 处置 |
|---|---|---|
| `speed` 该用逐帧 dt，全局 fps 抹平了 10 倍跨度 | 拿噪声当分母。speed 饱和率 1.9% → **5.8%**，逐帧抖动 `mean\|Δspeed\|` 0.162 → **0.215**（+33%） | **回退**，仍用整段 fps |
| 补一列 `frame_dt`，网络才知道每步跨多少真实时间 | 该列 = 纯时间戳噪声，零信息量，还是一条 train/serve skew 通道 | **不加** |

写进了 [bbox.py](../../app/services/inference/offline/blocks/bbox.py) 模块 docstring，防止下一轮又被"优化"回去。

## 实际改动

| 文件 | 改动 |
|---|---|
| `blocks/bbox.py` | 删 `t_norm/t_sin/t_cos` 三列；`effective_fps` 中位数 → 均值；`FEATURE_VERSION` → `clean_bbox_v4_notime`；模块 docstring 记下上述判据 |

`add_centered_window_stats` 的选列规则（按 `_present/_conf/_speed/_dist/_delta/_missing_age/_imputed` 后缀）不受影响——删掉的三列本来就不在其中，所以 148 = 68 + 2 + 2×39。

## 验证

- `pytest tests/` **465 passed**；pyflakes 零告警。
- 两条真实 step 产出 `68 / 70 / 148` 维，`effective_fps` 与真值逐位相符（14.987 / 14.998）。
- 无残留：全仓已无 `clean_bbox_v3_detectable` 与 `t_norm` 的代码引用（历史 update 文档保留原样，那是当时的事实）。

## 遗留

- **`speed` 的饱和阈值没有重估**。fps 修正后整段 speed 系统性放大 7.5~12.9%，饱和率随之从 1.9% 升到 2.4%（`1785995202505/2`）。clip 上界 5.0（归一化坐标/秒）是 v3 沿用下来的经验值，没量过是否仍合适——等新 ckpt 训出来看特征分布再定，现在改就是拍脑袋。
- **只有两条 step 的样本**。上述结论在这两条上很硬（三个证据一致、数值贴合理论值），但若换主机 / 换采集路径后 dt 出现真实掉帧（本地实测 `dt > 2×中位数` 占比 **0.00%**），逐帧 dt 的结论要重测。判据已写进 docstring。
