# 视频计时选型：媒体轴与墙钟轴的分工

> **文档类型**：选型与实测（2026-09-19 初稿，2026-09-20 重写）　**本文不记落地**，指针见 §6
> **依据来源**：实测（ffmpeg n7.1.4-9，本仓库 `.ffmpeg/bin/`，Windows）+ 代码分析。
> 标 **实测** 的数字是跑出来的，复现见 §5；其余是代码事实或由实测推出的结论。
> **知识库**：待沉淀 → [DESIGN_HLS_TIMELINE.md](../kb/DESIGN_HLS_TIMELINE.md)

## 结论

1. **媒体轴保持压紧**（`tfdt = Σ EXTINF`），墙钟不写进落盘二进制——因为同一份字节要同时
   被浏览器 MSE 和 ffmpeg 读，只有压紧轴在两边行为一致（§3）。
2. **UI 侧统一到媒体轴**——按当前需求（不要求"录像中断可见"）这是更省的一条：播放头不用
   换算、浏览器侧不用建映射表。墙钟只出现在出入口，由后端换算：告警落点换算后下发，
   送标区间换算后落库。**边界**：媒体刻度是瞬时坐标，持久化的时刻一律落墙钟（§2.2）。
3. **空洞可见成为要求时，三件事一起翻**：横轴换墙钟、播放头改每帧换算、清单补逐段
   `#EXT-X-PROGRAM-DATE-TIME`。映射载体取 PDT 而不是自研 JSON 侧信道；ffmpeg 不参与
   （实测它不读 PDT），后端换算始终在 Python 侧用清单 EXTINF 累加。
4. **不为空洞造数据**：进入重连先切出残帧段让空洞落到段边界，跨空洞的区间不裁剪也不导出。

> 本文只管选型与实测，做了什么见 §6。

## 1. 业务场景对时间轴提出了什么

### 1.1 一次采集产生两条不可互换的轴

前提是**分段落盘**：录像按 HLS fMP4 分段（`ca_segment_len` 300 帧一段），段因此是落盘、
查询、定位的最小单位——任何一个时刻最终都要落到「哪个段 + 段内偏移」。

**分段的理由不是实时回放**——没有边写边播的业务需求，读侧只面向已经跑完的 step。
分段来自三条与读侧无关的约束：CA 队列有内存上界（`ca_maxlen`，攒满一段就必须落盘）；
增量持久化（进程崩掉时已落盘的段仍然可用）；裁剪要按区间取字节而不是解整个大文件。
段长下限 `_MIN_SEGMENT_SECONDS = 5.0` 也只是在摊薄每段的 ffmpeg 固定开销。

写侧清单是 LIVE 形态（只追加、不写 `ENDLIST`），但那是追加写的形态，不是给谁 tail 播的；
读侧每次请求都现生成带 `ENDLIST` 的 VOD 清单。这条前提有一个直接推论，见 §2.2 的写入时机。

```text
墙钟轴   frame.timestamp = time.time()，epoch 毫秒
         全系统唯一的原始时刻：段文件名 {track}_segment_{ts_us}.mp4、
         raw_segment_*.idx 的逐帧原值、features.jsonl、告警 detected_at

媒体轴   EXTINF = 帧数 / eff_fps（段媒体时长）；tfdt = Σ EXTINF(0..N-1) × 90000（段落点）
         交给播放器与 ffmpeg 的段内坐标

媒体轴 = **压紧的墙钟**：段间空隙不存在，断流 30 s 在这条轴上宽度为零
```

两轴只在一个地方分岔：**断流**。段内丢帧不会让它们分岔（§4.2），所以分岔不是连续漂移，
是重连点上的阶跃。

### 1.2 三个场景

业务对这批段只做三件事，**三件都发生在 step 跑完之后**。每件事的输入与输出各在哪条轴上，
决定了它对时间轴的要求：

| 场景 | 操作 | 输入坐标 | 输出坐标 | 对时间轴的要求 | 回指 |
|---|---|---|---|---|---|
| **回放**含断流的录像 | 拖进度条、点告警标记跳转 | 墙钟（告警 `detected_at`） | 媒体（`<video>.currentTime`） | 进度条横轴与播放头同尺；段内匀速；空洞可见 | Q2 / Q5 |
| **圈一段送标** | 在回放页圈 `[t1, t2]` 提交 | 播放器给的媒体刻度 | 段文件 + ffmpeg `-ss` 的媒体偏移；样本元数据要墙钟 | 墙钟↔媒体可逆换算；段时长要有真值 | Q1 / Q6 / Q7 |
| **导出整个 step** | 下载整段录像作汇报素材 | 段集合 | 一个 mp4 | 段集合唯一；空洞不可跨 | Q3 / Q4 |

> Q 编号是落地记录用的稳定锚点，对照表在 §6。

### 1.3 三个场景收敛成三个问题

1. **墙钟与媒体的对应关系由谁声明、放在哪**——三个场景都要它，差别只在精度要求（§2.2）。
2. **断流在这个模型里是什么**：一段数据缺失，还是一个可以被抹平的细节（§4.1）。
3. **帧抖动要不要单独表达**——它和断流是两个层次的问题，不能套同一套机制（§4.2）。

#### 断流与帧抖动是两个层次

两者都让"采集是匀速的"这个假设失效，但失效的位置不同，因而能用的真值、能做的判定、
受影响的场景都不同：

```text
              断流重连                          帧抖动
────────────────────────────────────────────────────────────────────────
失效位置      段与段**之间**出现墙钟空洞        段**内部**帧间隔不均
两轴关系      在重连点上**阶跃**分岔            段级仍对齐（EXTINF ≈ 段墙钟跨度）
                                                失效的是"段内均匀"这个假设
量级          单次 ≤ cleanup_timeout(20s)，     帧间隔量级，累积在段内自相抵消
              多次累加
能表达它的    段级真值：清单的 (ts_us, EXTINF)   只有逐帧真值：`.idx` sidecar
              ——相邻条目一减就是空洞宽度        ——段级清单里它根本不可见
判定方式      可判定（gap_i > 0），可拒绝出片    不可判定为"错误"，它是正常采集形态
影响谁        跨段定位；成片的完整性断言         段内插值精度（只伤没有 .idx 的消费者）
```

结论上的差别：**断流要被看见、被判定、被拒绝；帧抖动只需要被精确换算，不需要被报告。**
把抖动当断流处理会在正常流上频繁误报；反过来把断流当抖动吸收，就是它今天被吞进段内变成
慢放的那条路径（§4.1）。

## 2. 选型

### 2.1 轴怎么排

| 方案 | 做法 | 优 | 劣 | 结论 |
|---|---|---|---|---|
| **压紧媒体轴** | `tfdt = Σ EXTINF`，墙钟留在文件名与清单文本里 | 播放器与 ffmpeg 行为一致；不改落盘二进制 | 需要一份外部映射；媒体刻度不能跨 step 比较 | **采用** |
| 墙钟轴 + 留洞 | `tfdt = 段墙钟 − step 起点`，gap 在轴上留空 | 两轴合一，不需要映射 | MSE `buffered` 出现空洞，hls.js 播到洞口停摆、不自己跨（[HLS_TIMELINE_PITFALL.md](../archive/resolved_issues/HLS_TIMELINE_PITFALL.md)）；同一份字节在 ffmpeg 侧是另一条轴——洞 ≤10 s 保留、>10 s 静默抹平（§3），导出的 mp4 与回放对不上，分界线藏在 ffmpeg 默认值里 | 否 |
| 墙钟轴 + 填充段 | 同上，且用黑屏帧把洞补满 | 两轴合一且连续，**所有换算变成恒等式**，前端与后端都不用实现映射 | 导出成片与送标 clip 里混入不存在的画面；这些产物的去向是标注样本与汇报素材，两者都要求画面与实际采集一一对应 | 否 |

决定性的技术事实是**同一份字节有两类消费者**：浏览器 MSE 走 `buffered` 语义，ffmpeg 走
`dts_delta_threshold` 语义，两者对"时间轴上的洞"处理方式不同（§3）。只有压紧轴在两边
给出同一条时间轴。

### 2.2 墙钟↔媒体的映射放在哪

| 方案 | 载体 | 优 | 劣 | 结论 |
|---|---|---|---|---|
| **全链路媒体坐标** | 不做映射；前端只报媒体刻度，后端单向换算出墙钟 | 前端上报的是它唯一能诚实给出的量；浏览器侧零换算，实现面最小 | 墙钟只在出入口存在，UI 上「当前这一帧几点拍的」算不出；空洞在压紧轴上宽度为零，画不出来 | **按当前需求采用** |
| 逐段 PDT | HLS 原生字段 `#EXT-X-PROGRAM-DATE-TIME`，每段一行 | 播放器解析清单时就把每个 fragment 的（墙钟, 媒体起点, 时长）一并解出，前端不用自建映射表；不新增真源——段墙钟本就在文件名里，PDT 只是写成播放器认识的形式；对 ffmpeg 零风险（实测案例 P） | 写侧每段多一行文本；前后端各自实现换算 | 空洞要可见时采用 |
| `/timeline` 增 `media_spans` 映射表 | 自研 JSON 侧信道 | 不动清单、不动播放器 | 映射信息 playlist 里本就有，JSON 是它的复制品 → 两处真源可能不一致；前端多一次 HTTP、多一套分段查找逻辑 | 否：同样要建映射表，且多一个真源 |

> **未验证项**：「播放器解析清单时把逐段墙钟一并解出」是 PDT 相对 JSON 侧信道的主要优势，
> 但 hls.js 暴露它的 API 形态（`fragment.programDateTime` 的可用时机与精度）**没有实测过**。
> 这条不成立的话，A 与 D 的差距只剩"不新增真源"一条。

#### 映射必须逐段写

HLS 允许只在首段声明 PDT、后续由播放器按 EXTINF 累加推导。而我们的媒体轴是压紧的，
累加推出来的正是"没有任何空隙"的那条轴——**推导结果会精确地把 gap 抹掉，反过来宣称从没
断过流**。逐段写才是在每个段上重新锚一次。只写首段不会报错、不会出画面问题，只会让整套
换算静默退回"两轴相等"的错误状态。

#### 写入时机：热路径逐段写，还是封档时整份补写

没有实时回放需求（§1.1），意味着**段落盘到 step 封档之间没有读者**。清单在这段窗口里可以
被整份重写，而不只是被追加。两种时机：

| 时机 | 做法 | 优势 | 代价 |
|---|---|---|---|
| **热路径逐段写** | `_m3u8.append` 每写一段多追加一行 PDT | 崩溃也不丢映射（已落盘的段自带锚点）；不引入新的生命周期钩子 | 只能声明"这一段首帧是几点"，空洞宽度得由读侧用相邻条目算术重建 |
| **封档时补写** | step 结束时按 health_monitor 记的断点重排一遍清单 | 断点是**声明式真值**，不必用 `gap_i` 反推，可去掉 §4.1 的阈值判断；还能顺带按空洞把清单切成若干内部连续的区段 | 封档失败或进程崩掉就没有映射，且崩溃恰恰是断流场景的近邻；新增一个必须成功的收尾步骤 |

**两者取热路径写**：PDT 是每段一行的局部事实，写它不需要等到封档；而封档补写把一份本来
崩不丢的数据变成依赖收尾成功。封档窗口留给**空洞真值**更合适——那是一个跨段的全局事实，
算术重建（`gap_i > 0`）只是在没有声明源时的替代（§4.1）。

#### 换算式是恒等式，不是插值

```text
目标墙钟 t
  → 段 i    = 清单里起点 ts_us ≤ t 的最后一段
  → 帧号 k  = 段 i 的 .idx 里 t 落在第几帧        （raw 轨才有 .idx）
  → 媒体秒  = Σ_{j<i} EXTINF_j  +  k × EXTINF_i / N_i
```

段内那一项是精确的：cv2 以 `eff_fps` 等间隔写 N 帧，第 k 帧的媒体时刻恰为 `k / eff_fps`，
而 `EXTINF = N / eff_fps`，故 `k / eff_fps ≡ k × EXTINF / N`。**精确性不依赖采集匀速，
只依赖"cv2 等间隔写帧"**——有 `.idx` 的 raw 轨在任何抖动/断流下都精确。拿不到这份精确的
两处见 §4.3。

#### PDT 给谁用：只有"高频本地换算"需要它

PDT 的收益不是**能力**，是**省一次往返**：凡是后端能预先算好、随 `/timeline` 一起下发的
量，浏览器侧都不需要本地映射表。所以要逐条问的是"这个量的刷新频率，后端来不来得及算"。

前提是**回放页的进度条是页面自绘的**（`.timeline-strip`），不是 `<video controls>` 的原生
进度条。原生那条只能拖，认不得告警、画不了区间与禁区；标记、已选区间、待加入区间、播放头
游标都画在自绘条上，点击定位也由它接管。这决定了横轴用哪条轴由我们自己定。

| 功能 | 浏览器侧要本地映射吗 | 说明 |
|---|---|---|
| **点击告警标记跳转** | **否** | 落点由后端换算成 `media_offset_ms` 随 `/timeline` 下发，媒体刻度直接就是 `currentTime`——浏览器侧全程不碰墙钟 |
| 打点圈区间并上报 | 否 | 上报媒体刻度，墙钟由后端换算后随响应带回 |
| 进度条横轴与播放头 | **取决于横轴选哪条** | 见下方「横轴选型」——选媒体轴不需要，选墙钟轴则播放头每帧都要换算 |
| **显示"当前播放是几点"** | **是——唯一一个** | 每个 `timeupdate` 都要重算，后端无法预先下发（值随播放头连续变），往返也跟不上 |
| 空洞禁区绘制 | 间接是 | 禁区本身是静态低频数据，后端一次下发 `gaps` 即可；但**画禁区要求横轴换成墙钟**，而墙钟横轴下播放头每帧都要 media→wall，于是又回到上一行 |
| 后端裁剪的 seek 基准 | 否 | ffmpeg 不读 PDT（§3 实测），后端在 Python 侧用清单 EXTINF 累加自己算 |
| 影响导出 / 裁剪产物 | 否 | 这正是它可以安全加进清单的原因 |

**所以用户最直观的那个功能——点击告警标记跳到对应画面——恰恰是最不需要 PDT 的一个。**
它今天能对，靠的是后端把墙钟告警换算成媒体刻度再下发。浏览器侧真正剩下的高频换算只有
"当前几点"一项，以及由它牵连出来的墙钟横轴。**这就是全链路媒体坐标能当最小解的原因**，
代价也正好是那一项：时间显示退成片内相对时间，空洞跟着画不出来。

#### 横轴选型：媒体轴还是墙钟轴

进度条上要同时摆三样东西——横轴全长、播放头、告警标记（加上想画的空洞禁区）。**硬约束
只有一条：全长与播放头必须同尺。**两者各取一条轴就是缺陷 #2 的成因：全长取墙钟跨度
（含 gap）、播放头取 `currentTime`（Σ EXTINF），10 分钟含一次 20 s 断流的 step 播到底
指针只走到 96.7%。

剩下的自由度就是选哪条轴，两条都自洽，差别在换算被推到哪一侧：

| 横轴 | 全长 | 播放头 | 告警标记落点 | 空洞 | 浏览器侧要本地映射吗 |
|---|---|---|---|---|---|
| **媒体轴** | Σ EXTINF（`media_duration_ms`） | `currentTime` **直接就是刻度** | 后端把 `detected_at` 换算成 `media_offset_ms` 下发 | 宽度为零，**画不出** | 否 |
| **墙钟轴** | 墙钟跨度（含 gap） | 每帧 media→wall **换算一次** | `detected_at` 直接摆 | `gap_i` 就是宽度，**可画** | 是（高频，见上表） |

换算的总量是守恒的，只是位置不同：**媒体轴把换算推给后端**（告警标记，低频、可预算、
一次下发）；**墙钟轴把换算推给浏览器**（播放头，每个 `timeupdate` 一次，只能本地做）。

**按当前需求取媒体轴。** 墙钟轴只在一件事上更强——空洞可见（压紧的媒体轴上那 20 秒宽度
为零，占不到像素，禁区无处可画），而"录像中断必须可见"目前不是业务要求。除这一项外媒体
轴在每一行上都更省：播放头不用换算、映射表不用建、PDT 不用写、hls.js 的 API 形态不用验。

**翻转条件写在这里**：巡检审计提出"中断必须可见"时，三件事一起翻——横轴换墙钟、播放头
改为每帧换算、清单补逐段 PDT。它们是一个决定，不能分开取。

#### 媒体刻度是瞬时坐标，不是持久标识

统一用媒体轴的前提是守住一条边界：**媒体刻度只在"当前这次回放/这次请求"内有效**，
凡是要存下来、跨系统传递、跨 step 或跨轨比较的时刻，必须先换算成墙钟再落。

理由是媒体刻度的含义依赖段集合，而段集合会变：

```text
同一个 media_ms 指向哪一帧，取决于它前面有哪些段、各自多长
  → 孤儿段被补登记、过期段被清理，前缀和就变了，同一个刻度指向另一帧
  → 两轨的 Σ EXTINF 不同尺（processed 起步晚于取流），raw 的刻度画到 processed 上是错的
墙钟没有这个性质：它由采集那一刻决定，与盘上还剩哪些段无关
```

这条边界今天是守住的——送标样本的 LS meta 同时写两套坐标
（[`lab.py:516-525`](../../app/routers/lab.py#L516-L525)：`start_ms`/`end_ms` 是墙钟真值，
`start_media_ms`/`end_media_ms` 是请求回显）。UI 上"选区条在 processed 轨隐藏"也是同一条
边界的体现：`clips[]` 存的是 raw 的媒体刻度，换轨后分母不同尺，画上去位置是错的。

> **与本文初稿相反**：初稿主张"保持墙钟横轴、只改播放头"，当时把墙钟横轴当成既定前提。
> 正确的说法是横轴本身就是选项，且它与空洞可见性是同一个决定——要空洞就要墙钟轴，
> 要墙钟轴就要 PDT。三件事绑在一起，不能分开取舍。

### 2.3 「有哪些段」的真源：清单，不是文件系统

一条 playlist 条目同时给出墙钟锚点与媒体长度，**无需 join 两个来源**：

```text
#EXT-X-PROGRAM-DATE-TIME:2026-09-19T12:00:00.000Z   ← §2.2 方案新增：该段首帧墙钟
#EXTINF:10.013,                                      ← 该段媒体长度
raw_segment_1700000000000000.mp4                     ← 文件名里的 ts_us 就是墙钟锚点

tfdt  = Σ 前面各段的 EXTINF                            ← 写侧算，读侧不用
gap_i = seg_{i+1}.ts_us − (seg_i.ts_us + EXTINF_i × 1e6)   ← 断流空隙
```

选它而不是文件系统枚举，三条理由：

1. **一个真源。** 文件系统答"段在不在"、清单答"登记没登记"，两者不重合的窗口是段已落盘
   未登记，读侧每个函数得各自记住自己的入口含不含在途段。
2. **修掉一整类静默失败。** 把未登记段喂给 ffmpeg 命中
   [DESIGN_SEGMENT_CONCAT.md](../kb/DESIGN_SEGMENT_CONCAT.md) §5.3：exit 0、任何日志级别都
   无输出、`-xerror` 抓不住，产出结构完整、ffprobe 满意、能正常播放、但少了一截的 mp4。
   判据从"文件在不在"换成"条目在不在"，这类失败在入口就没了。
3. **实测快 32 倍**（Windows，540 项的 step 目录 = 180 段 × 双轨 + sidecar）：

```text
读 m3u8 + 解析                       0.216 ms/次
os.scandir + is_file + 正则          0.432 ms/次
Path.iterdir + is_file + 正则        6.925 ms/次
内存 bisect 单次段级定位              0.0001 ms/次     ← 定位本身不是成本
```

差距里大部分是 `Path.is_file()` 对 540 个目录项各发一次 stat。这是副产品不是理由。

**代价，已知并接受**：

| 代价 | 说明 |
|---|---|
| 未登记段的帧对离线反查不可达 | 成因只有两种：清单 append 抛 `OSError`，或进程崩在 `os.replace(段)` 与 append 之间。这些文件本身是完整可解的 fMP4，只是没登记。概率低、路径本就异常 |
| 404 / 503 两档诊断塌成一档 | 今天靠"盘上有段 vs 清单有条目"分出「挑错 track」和「首段还在转码，再等等」。收口后两者都表现为"清单不存在"。**代价本身也小**：读侧只面向跑完的 step（§1.1），"再等等"那一档只在异常路径出现，不是常态 |

### 2.4 四个不能拿来定位的数

| 数 | 为什么不行 |
|---|---|
| `tfdt` | 派生量；且子集会被 ffmpeg 归一到 0（实测案例 6/7），绝对值不可依赖 |
| `/timeline` 的 `duration_ms` | 墙钟跨度（含 gap），与 `<video>.duration`（Σ EXTINF）不同尺，两者混用就是进度条的两把尺 |
| 相邻段 ts 中位差 | 盘上的第三套段时长口径，遇 gap 失真。段的墙钟长度直接用 EXTINF 即可 |
| 文件系统枚举 | 它答的是"盘上有什么文件"，那不等于"有哪些段"（§2.3） |

## 3. 决策所依赖的实测：ffmpeg 的时间轴只来自 tfdt，不读 EXTINF

材料刻意让两者错开（仓库原有材料两者天然一致、区分不了）：3 个 fMP4 fragment，各 20 帧
@10fps = 2.000 s 媒体时长，timescale 90000，共用一份 init。**每帧是一块纯灰，灰度值编码它
的全局帧号**——解出来的画面能反查"这是源里第几帧"，从而判定 seek 落点，而不只是看时长。

```text
#    tfdt(媒体轴落点)     EXTINF(清单声明)   命令              产物                      判定
────────────────────────────────────────────────────────────────────────────────────────────
1    0 / 2 / 4 s          2.0 × 3            -c copy           6.000s、60 帧、源帧 0–59   基线
2    0 / 2 / 4 s          3.0 × 3（虚高）     -c copy           6.000s、60 帧、源帧 0–59   与基线逐帧相同
8    0 / 2 / 4 s          0.1 × 3（1/20）    -c copy           6.000s、60 帧、源帧 0–59   与基线逐帧相同
P    0 / 2 / 4 s          2.0 × 3 **+ PDT**  -c copy           6.000s、60 帧、源帧 0–59   与基线逐帧相同
────────────────────────────────────────────────────────────────────────────────────────────
4    0 / 2 / 4 s          3.0 × 3（虚高）     -ss 3.0（输出侧） 首帧 = 源帧 30             听 tfdt
4b   0 / 2 / 4 s          2.0 × 3（真值）     -ss 3.0（输出侧） 首帧 = 源帧 30             与 4 相同
────────────────────────────────────────────────────────────────────────────────────────────
5    子集 2 / 4 s         2.0 × 2            -ss 0.5           首帧 = 源帧 25             首段归一到 0
6    子集 100 / 102 s     2.0 × 2            -ss 0.5           首帧 = 源帧 25             与 5 相同
7    子集 100 / 102 s     2.0 × 2            -c copy           start_time=0、4.000s       绝对 tfdt 被归零
────────────────────────────────────────────────────────────────────────────────── 洞的阈值 ──
3a   0 / 3 / 6 s（洞 1s） 2.0 × 3            -c copy           8.000s、包仍 60、解码 80 帧 洞保留，冻结上一帧
3b   0 / 7 / 14 s（洞 5s）2.0 × 3            -c copy           16.000s                    洞保留
3c   0 / 11 / 22 s（洞 9s）2.0 × 3           -c copy           24.000s                    洞保留
3d   0 / 17 / 34 s（洞 15s）2.0 × 3          -c copy           6.000s                     洞被**静默抹平**
3e   同 3d                2.0 × 3            -dts_delta_threshold 20  36.000s             洞又保留了
3f   同 3b（洞 5s）        2.0 × 3            -dts_delta_threshold 2   6.000s              洞被抹平
────────────────────────────────────────────────────────────────────────────────────────────
```

四条结论，各自判了哪个方案：

| 实测结论 | 用在哪 |
|---|---|
| **ffmpeg 的时间轴完全来自 `tfdt` + sample duration，EXTINF 写成什么都不影响产物**（案例 2 与 8：虚高 50%、缩到 1/20，逐帧产物与基线相同） | 后端裁剪的 seek 基准**本来就是媒体轴**；任何"往临时清单写墙钟 EXTINF 来对齐 `-ss`"的做法是空操作 |
| **子集的首段 tfdt 被归一到 0**（案例 6/7：100 s 的绝对落点照样得到 `start_time=0`） | `-ss` 是"相对首个选中段的媒体起点"；tfdt 不可用于定位（§2.4） |
| **`EXT-X-PROGRAM-DATE-TIME` 对 ffmpeg 是明示无效的**（案例 P） | 逐段 PDT 对 ffmpeg 零风险；同时说明 PDT 修不了后端裁剪 |
| **段间空洞只在 10 秒以内会被保留，超过就被静默抹平**（案例 3a–3f），机制是 `-dts_delta_threshold`（默认 10 s） | 否掉"墙钟轴 + 留洞 / 填充"两个方案（§2.1） |

### PDT 对 ffmpeg 无效，且是明示的

不用推断，`-loglevel info` 直接把它打出来，一段一行：

```text
[hls @ ...] Skip ('#EXT-X-PROGRAM-DATE-TIME:2026-09-19T12:00:00.000Z')
[hls @ ...] Skip ('#EXT-X-PROGRAM-DATE-TIME:2026-09-19T12:00:02.000Z')
[hls @ ...] Skip ('#EXT-X-PROGRAM-DATE-TIME:2026-09-19T12:00:32.000Z')
```

`ffprobe -show_format -show_streams` 的 tag 里也没有它的任何痕迹。**ffmpeg 既不用它、也不
透出它**——推论：墙钟映射不可能经 PDT 传给 ffmpeg，后端要的 wall→media 换算只能在 Python
侧用清单的 EXTINF 累加算出来，再把算好的秒数交给 `-ss`。

### 段间空洞的 10 秒阈值

洞开到 1 / 5 / 9 秒，ffmpeg 保留（时长被撑到 8 / 16 / 24 s）；开到 15 秒，**产物缩回
6.000 s，洞没了，exit 0、无警告**。加 `-dts_delta_threshold 20` 洞就回来了，把阈值压到 2
洞又没了——确认是 `dts_delta_threshold` 在判：跳变大于阈值按"不连续"处理、重基时间戳；
小于阈值当真实空洞保留。

对本次选型是决定性的：若把 tfdt 改成墙钟，同一份字节在两类消费者手里会给出两条不同的
时间轴——浏览器按洞停摆，而 ffmpeg 导出时短洞保留、长洞抹平。

> **EXTINF 只是对 ffmpeg 无效，播放器仍然读它**：`<video>.duration`、seek 选段、缓冲与
> TARGETDURATION 判断都吃它，写错会出段尾 MSE 缓冲洞与总时长缩水。本节结论只覆盖 ffmpeg
> 消费端，不放松写侧 EXTINF 的正确性要求。

## 4. 边界情况

### 4.1 断流重连

**分岔量 = 断流累计时长。** 同一 run 内重连不清目录、直接续写（重连只 respawn decoder，
CQ 对象不换；目录只在"本代 CQ 首写"时才被 supersede 清掉），断流前后的段进同一条 playlist，
EXTINF 照常累加、tfdt 照常接续。放弃重连的阈值是 `cleanup_timeout`，默认 **20 s**，
所以单次重连引入的分岔 ≤ ~20 s，**多次重连累加**。run 重启走整目录 supersede，没有此问题。

#### 空洞默认不落在段边界，先把它切出来

切段是**纯计数切**：只拉攒满 `ca_segment_len`（300 帧）的整段，不足一段的残帧只在拆除时
收尾，而重连不拆除。断流那一刻攒在队列里的半批帧留在原地、被重连后的帧补满，拼成一个
横跨 gap 的段。拿真代码跑（`raw_fps=30`、段长 300 帧、gap = 20 s）：

```text
断流前已攒   eff_fps    EXTINF     真实内容    慢放     墙钟跨度
──────────────────────────────────────────────────────────────
    1 帧      9.99      30.03s     10.00s    3.00x    29.93s
   75 帧      9.99      30.03s     10.00s    3.00x    29.93s
  150 帧      9.99      30.03s     10.00s    3.00x    29.93s
  299 帧      9.99      30.03s     10.00s    3.00x    29.93s
──────────────────────────────────────────────────────────────
  无断流      30.00     10.00s     10.00s    1.00x     9.97s
```

**"断流前已攒了多少帧"完全不影响结果**——`eff_fps` 只看首末帧跨度，而跨度恒为
「10 s 内容 + 20 s gap」。该段 `eff_fps` 从 30 掉到 9.99（仍在合理带 `[1,60]` 内，
**不触发退化兜底**），
cv2 就按 9.99 fps 把 300 帧写下去：10 秒的真实画面被拉成 30 秒慢放。

这一条同时使两轴在**段边界上仍然对齐**：`EXTINF(30.03 s) ≈ 墙钟跨度(29.93 s)`，`gap_i`
算出来是 0.1 s 而不是 20 s。**这不是公式错**——那一段的 EXTINF 确实覆盖了它的墙钟跨度，
失真跑到了段**内部**。

最佳实践是**判定断流的那一刻就把队列里的残帧单独切成一个短段**，不等它被重连后的帧补满：

| 决策 | 原因 |
|---|---|
| 必须在**进入**重连时切，不能在重连**成功**时切 | 成功判定的依据就是"已经来了新帧"，那时残批里已混进重连后的帧，段仍横跨 gap（只是被吞的比例变了），慢放照旧 |
| 栅栏用时间戳而不是帧数上限 | 断流判据是 decoder 子进程死活（`check_interval` 1.0 s），respawn 也可能在 1 s 内恢复推帧。`fence_ts = 最后一帧 ts` 与调用时机、与此前拉走了多少整段都无关 |
| 它是空洞可见性的前提 | 空洞不落到段边界，PDT 差值算出来 ≈0、`gap_i` 也不是真值，禁区绘制与拒绝判据都失去输入 |

**代价**：每次重连多落一个不足 300 帧的短段，是合法 HLS 段，无特殊处理。

#### 空洞的表达：不造数据，也不静默粘合

| 决定 | 理由 |
|---|---|
| 媒体轴上宽度仍为零（不造填充段、不写黑屏帧、不改 tfdt） | 填充帧会进入标注样本与汇报素材（§2.1） |
| 墙钟轴上由 `gap_i` 画成不可选中的禁区 | 压紧的媒体轴上空洞宽度为零，画不出"一段"；只有铺在墙钟轴上那 20 秒才占得到位置 |
| **任何跨越空洞的区间都不产出成片**，裁剪与整段导出同档 | 产物的区间元数据声称覆盖 `[t1, t2]`，而内容少了中间 20 秒，两者不一致。不按断言强度分档——裁剪 clip 与整段导出都会流向汇报与标注 |
| 判据 `gap_i > 0` 必须三处同源（`/timeline` 的 gaps 字段、裁剪校验、导出校验） | 三处各写一份会漂移 |
| 拒绝要在前后端各做一次 | 前端置灰只管交互，API 可被直接调用 |

连续性判据因此从启发式（"相邻段 ts 中位差 + 容差"）换成精确式：真值在 EXTINF 里，容差与
段长估算两个可配参数一并退役。

`gap_i > 0` 仍是**算术重建**——它从段的起止推断"中间断过"，而真正知道断点的是
health_monitor。更彻底的做法是让它在封档时把断点直接写进清单（§2.2 的写入时机），判据就从
重建变成读取，连保守阈值都不需要。没有实时回放需求使这个窗口存在；本次不做，因为它要求
封档步骤必须成功，而断流与崩溃是近邻场景。

> **代价说清楚**：一个 10 分钟的 step 只要断过一次流，整段原片就取不到了。拿不到的是
> **成片**，不是数据——段、`.idx`、features 全在盘上，离线反查照常工作。
> 若日后确实需要取原片，放宽的方向是**按空洞切成多个文件**（每个文件内部连续、文件名带
> 各自的墙钟区间），而不是放行一个跨空洞的单文件。

#### 为什么不用 `#EXT-X-DISCONTINUITY`

它表达的是"编码参数变了"（timescale / codec / PTS 基准重置），不是时间空白——断流前后编码
参数没变，写它会误导播放器。将来换轨或换编码参数时才是它的场景。

### 4.2 网络抖动

抖动与断流是两个层次（§1.3）：断流破坏的是段**之间**的连续性，抖动只破坏段**内部**的
匀速。所以这一节不引入任何新的判定或上报机制——抖动不是错误，它是正常的采集形态。

**段内丢帧不会让两轴分岔，不需要额外机制。** `eff_fps` 由首末帧跨度反推，丢帧同时压低 `N`
与 `eff_fps`，`EXTINF = N / eff_fps ≈ 段墙钟跨度`。段级的对应关系自动保持。

代价落在段**内部**：段不再匀速，靠比例插值的消费者误差上升（§4.3）。有 `.idx` 的 raw 轨
不受影响——换算是恒等式，只依赖"cv2 等间隔写帧"（§2.2）。

| 抖动形态 | 行为 | 处理 |
|---|---|---|
| **亚秒～数秒停顿** | 不触发断流判据（decoder 子进程仍活着），残帧不切出，该段轻微慢放 | 接受。量级从 20 s 降到数秒，没有消失 |
| **反复死/活** | 每次重连各切出一个短段，连出若干不足 300 帧的段 | 接受。都是合法 HLS 段 |
| **只有 1 帧的残段** | 撞退化兜底：`eff_fps` 回落 15.0、`EXTINF = 0.067 s` | 接受。该段自洽（tfdt / mdhd / EXTINF 三者一致、播放不出洞），失真被限制在段内部 |
| **跨 gap 段的 `eff_fps = 9.99`** | 仍在合理带 `[1, 60]` 内，**不触发兜底、无任何报警** | 合理带是编码器输入校验，不是断流检测器。断流检测必须独立做（§4.1） |
| **processed 轨积压** | processed 由 viz worker 按 tick 渲染，ts 落后 raw 一个推理管线延迟；延迟内积压超过一整段时，跨 gap 的那批会先被当整段拉走 | processed 是参考轨，送标与精确定位走 raw |

### 4.3 换算精度的两个盲区

两处拿不到 `.idx`，段内只能按比例插值：

| 谁 | 正常段误差 | 跨 gap 段误差 |
|---|---|---|
| processed 轨（有意不产 `.idx`） | ≤ 一帧 | 最大 ≈ gap（~20 s） |
| 前端（浏览器侧只有 PDT + EXTINF） | ≤ 一帧 | 最大 ≈ gap（~20 s） |

前端那一行决定入参：**打点上报的坐标由它算出**，后端换算再精确也纠正不了一个已经算错的
入参。这是空洞必须先落到段边界（§4.1）的第二个理由——段内恢复匀速之后，比例插值就精确了。

## 5. 复现方法

探针脚本 `probe.py`（stdlib + 仓库自带 ffmpeg，不依赖 app 包）留在 `E:/tmp/timebase_probe/`，
**不入库**——它造的材料是一次性的。要重做：

```bash
# 造材料：3 段 × 20 帧 @10fps，每帧纯灰、灰度 = 8 + 4×全局帧号，timescale 90000，共用 init
"$FF" -framerate 10 -start_number {0|20|40} -i f%03d.pgm -frames:v 20 \
  -c:v libx264 -preset veryfast -crf 18 -pix_fmt yuv420p -an \
  -hls_segment_type fmp4 -hls_segment_options video_track_timescale=90000 \
  -hls_fmp4_init_filename init.mp4 -hls_segment_filename 'fragment_%d.mp4' \
  -start_number 0 -hls_time 99999 -hls_list_size 0 -f hls index.m3u8

# 改 tfdt：复用 app/storage/hls/_fmp4.py 的 box 遍历（moof→traf→tfdt，v1 是 64-bit）
# 手写清单：EXTINF 取要验的值，#EXT-X-MAP:URI="init.mp4"，带 #EXT-X-ENDLIST
"$FF" -y -allowed_extensions ALL -i probe.m3u8 [-ss X -to Y] -c copy out.mp4

# 判读落点：解成灰度裸流，取每帧中心像素 → 反查全局帧号
"$FF" -v error -i out.mp4 -f rawvideo -pix_fmt gray - | <取第 k 帧中心字节，(px-8)/4 即源帧号>

# PDT 被跳过（案例 P）：清单里加 #EXT-X-PROGRAM-DATE-TIME 行，看 demuxer 自己说
"$FF" -allowed_extensions ALL -i pdt.m3u8 -f null - 2>&1 | grep "Skip"
#   → [hls @ ...] Skip ('#EXT-X-PROGRAM-DATE-TIME:...')   一段一行

# 空洞阈值（案例 3a–3f）：tfdt 拉开 N 秒，看产物时长是被撑开还是缩回 6.000
#   洞 1/5/9s → 8/16/24s（保留）；洞 15s → 6.000s（抹平）
"$FF" -y -allowed_extensions ALL -dts_delta_threshold 20 -i probe.m3u8 -c copy out.mp4
#   → 洞 15s 加了这个参数就变 36.000s，确认是 dts_delta_threshold 在判
```

> **测材料有状态，逐例都要重打 tfdt。** 初稿的案例 P 就是在上一例遗留的 tfdt（0/100/102 s）
> 上跑的——结论碰巧没变（PDT 确实无影响），但那次的 6.000 s 是 ffmpeg 触发了 10 秒阈值把
> 98 秒跳变重基凑出来的，不是基线。已用干净材料重测。
