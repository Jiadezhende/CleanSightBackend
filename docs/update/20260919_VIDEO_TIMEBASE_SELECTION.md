# 视频计时选型：媒体轴不换，墙钟逐段声明，空洞显式化且不可裁剪

> **变更状态**：选型与实测（2026-09-19）　**本文不记落地**，两份落地记录见 §5 的指针表
> **知识库**：待沉淀 → [DESIGN_HLS_TIMELINE.md](../kb/DESIGN_HLS_TIMELINE.md)
>
> **依据来源**：实测（ffmpeg n7.1.4-9，本仓库 `.ffmpeg/bin/`，Windows）+ 代码分析。
> 标 **实测** 的数字是跑出来的（复现见 §6）；其余是代码事实或由实测推出的结论。
>
> **本稿是 0919 初稿的重组**：结论与数据均未变，读法改为「现状全景 → 改造后全景 →
> 逐问题点新老实现对比」。**落地时推翻了初稿的若干判断，见 §5 指向的两份落地记录。**

## 结论

**三个决定**：①**轴不换**——媒体轴继续压紧（`tfdt = Σ EXTINF`），墙钟改由 playlist 的
`#EXT-X-PROGRAM-DATE-TIME` **逐段**声明；②**段查询收口到清单**——清单里有条目的才是段，
文件系统枚举退出查询路径；③**空洞显式化**——进入重连先 flush 残帧让空洞落到段边界，
进度条按墙钟轴把它画成不可选中的禁区，跨空洞的区间不裁剪也不导出，**不造填充帧**。

**改这些是为了修 4 处已在线上的 P1**（送标裁剪错位、告警跳转错位、裁剪静默截短、跨断流段
3× 慢放），不是为了美观。实测同时推翻一个既有假设：`clip_builder` 写进临时清单的那套
"墙钟 EXTINF" 对 ffmpeg 是空操作。

> **⚠ 实际落地范围比本节小。** 上面第 ③ 条里空洞相关的部分（逐段 PDT、禁区绘制、跨空洞
> 拒绝出片）**整块降级**，本轮未做；缺陷 #1/#2 改由"前端上报媒体坐标 + 后端换算墙钟"解决，
> 进度条横轴改成媒体轴而非墙钟轴。**本文只管选型与实测；实际做了什么见 §5 的指针表。**

## 1. 现状全景

### 1.1 一条墙钟进来，两条轴出去，三个消费者各取一条

```text
写侧                                   盘上                                    读侧
─────────────────────────────────────────────────────────────────────────────────────
frame.timestamp = time.time()  ─┬─墙钟轴→ 段文件名 {track}_segment_{ts_us}.mp4
  epoch 墙钟，全系统唯一原始时刻 │        raw_segment_*.idx      逐帧墙钟原值
  decoder.py:367                │        features.jsonl / 告警 detected_at
                                │
                                └─媒体轴→ EXTINF = 帧数 / eff_fps        段媒体时长
                                         tfdt   = Σ EXTINF(0..N-1)×90000 段落点

                  媒体轴 = **压紧的墙钟**：段间空隙不存在，断流 30 s 在这条轴上也不存在
```

```text
消费者                       吃哪条轴                          墙钟↔媒体怎么换算
────────────────────────────────────────────────────────────────────────────────
hls.js / MSE 回放            媒体轴（tfdt 定位、EXTINF 估算）   **今天：假设两轴相等**
lab 打点 → clip_builder      入参是墙钟 ms，seek 落在媒体轴     **今天：假设两轴相等**
离线帧反查 FrameTracker      纯墙钟（`.idx`，不碰视频时间轴）    不需要换算
```

### 1.2 今天那条恒等式什么时候不成立

**两轴只在一个地方分岔：断流。** 段内丢帧不会让它们分岔——`eff_fps` 由首末帧跨度反推，
丢帧同时压低 `N` 与 `eff_fps`，`EXTINF = N/eff_fps ≈ 段墙钟跨度`。所以分岔不是连续漂移，
是重连点上的**阶跃**。

分岔量 = 断流累计时长。同一 run 内断流重连**不清目录、直接续写**：重连只 respawn decoder，
CQ 对象不换（[`health_monitor/manager.py`](../../app/services/health_monitor/manager.py) 的
respawn 循环），而目录只在"本代 CQ 首写"时才被 supersede 清掉
（[`recording/service.py:285-288`](../../app/services/recording/service.py#L285-L288)）。
断流前后的段进同一条 playlist，EXTINF 照常累加、tfdt 照常接续，媒体轴上那段停顿不存在。
放弃重连的阈值是 `cleanup_timeout`，默认 **20 s**
（[`health_monitor/config.py:29`](../../app/services/health_monitor/config.py#L29)），
所以单次重连引入的分岔 ≤ ~20 s，**多次重连累加**。run 重启走整目录 supersede，没有此问题。

错位的闭式解（记 `T_m` = 播放器当前媒体时刻，`W0` = step 首段墙钟，`G(t)` = 媒体时刻 t
之前的累计断流时长）：

```text
前端上报         abs_ms = W0 + T_m                     ← 假设两轴相等（index.html:572）
该帧真实墙钟     W0 + T_m + G(T_m)
                 ───────────────────────────────────
                 上报值系统性**偏早** G(T_m)

clip_builder     offset = abs_ms − 首选中段墙钟 ts     ← clip_builder.py:297
真实媒体偏移     T_m − 首选中段媒体起点
                 ───────────────────────────────────
                 误差 = G(首选中段)，裁出的内容**早了 Σgap**
```

段的挑选（`_select_segments` 按墙钟 ts 相交）与段内 seek 偏移**同向偏移同一个量**，所以
不越界、不报错——整条 clip 一致地早了 Σgap。这就是"线上一直能用"的原因：没发生过重连的
step 里 `G ≡ 0`，恒等式成立。

## 2. 改造后全景

### 2.1 同一张图，改造后

```text
写侧                                   盘上（清单是唯一真源）                  读侧
─────────────────────────────────────────────────────────────────────────────────────
frame.timestamp = time.time()  ─┬─墙钟轴→ #EXT-X-PROGRAM-DATE-TIME  **新增**，逐段
                                │        段文件名 {track}_segment_{ts_us}.mp4  不变
                                │        raw_segment_*.idx / features          不变
                                │
                                └─媒体轴→ EXTINF / tfdt                        不变，仍压紧

进入重连时 flush 残帧
  ⇒ 空洞只出现在**段边界**
  ⇒ gap_i = seg_{i+1}.ts_us − (seg_i.ts_us + EXTINF_i × 1e6)   给出真值
```

```text
消费者                       吃哪条轴                        墙钟↔媒体怎么换算
────────────────────────────────────────────────────────────────────────────────
hls.js / MSE 回放            媒体轴播放                      hls.js 的 fragments[]
                                                             (programDateTime, start,
                                                              duration) = 分段映射表
lab 打点 → clip_builder      入参墙钟 → Python 侧换算 → -ss  清单 (ts_us, EXTINF) 逐行表
                                                             + `.idx` 逐帧真值（raw 轨）
离线帧反查 FrameTracker      纯墙钟                          不需要换算（不变）
进度条 / 禁区                 墙钟横轴                        gap_i 直接画
```

### 2.2 改造后系统靠三条不变量成立

1. **一切"查"与"定位"都在墙钟轴上。** 媒体轴不是能拿来查的坐标——它是压紧的，同一个媒体
   秒数在断流历史不同的两个 step 里对应不同的现实时刻。它只是"交给播放器 / ffmpeg 的那段
   字节内部的坐标"，是换算的**终点**，不是起点。
2. **"有哪些段"只由清单回答。** 盘上有文件但清单没条目 = 不是段。
3. **落盘一个字节都不为空洞而写。** 空洞在媒体轴上宽度为零，只活在墙钟轴与 UI 上；
   跨空洞的区间不产出任何成片。

### 2.3 老 → 新 一屏对照

| | 今天 | 改造后 |
|---|---|---|
| 媒体轴（tfdt / EXTINF） | 压紧 | **压紧，不动** |
| 墙钟在清单里 | 只有文件名里的 `ts_us` | 文件名 `ts_us` **+ 逐段 PDT** |
| wall→media 换算 | 不存在（假设相等） | 前端用 `fragments[]`，后端用清单 + `.idx` 恒等式 |
| "有哪些段" | 文件系统枚举 ∩ 清单（视函数而定） | **清单，唯一** |
| 空洞落在哪 | 被某一段吞掉，段内 3× 慢放 | **段边界**，段内恢复匀速 |
| 空洞可见吗 | 不可见（静默粘合） | 进度条上的不可选中禁区 |
| 跨空洞裁剪 / 导出 | 放行，产出"看起来连续"的 mp4 | **一律拒绝**，服务端独立校验 |
| 进度条横轴 | 墙钟（`duration_ms`） | 墙钟，**不变** |
| 播放头位置 | `currentTime` 全局线性 → 假墙钟 | `currentTime` → **分段映射** → 真墙钟 |
| 段时长口径 | 三套（EXTINF / 相邻 ts 差 / 中位差估算） | **一套：EXTINF** |
| 连续性判据 | 中位差 + `gap_tolerance_ms` 容差 | `gap_i > 0` 精确式 |
| 落盘二进制 / 新增接口 | — | **都不动**（PDT 是清单里的一行文本） |

### 2.4 红线：四个不能拿来定位的数

| 数 | 为什么不行 |
|---|---|
| `tfdt` | 派生量；且子集会被 ffmpeg 归一到 0（实测案例 6/7），绝对值根本不可依赖 |
| `/timeline` 的 `duration_ms` | 墙钟跨度（含 gap），与 `<video>.duration`（Σ EXTINF）不同尺，两者混用就是 Q5 |
| `_est_segment_duration_us`（相邻段 ts 中位差） | 盘上的第三套段时长口径，遇 gap 失真。段的墙钟长度直接用 EXTINF 即可 |
| **文件系统枚举**（`iterdir` + 文件名正则） | 本轮起不再是查询入口。它答的是"盘上有什么文件"，那不等于"有哪些段" |

## 3. 逐问题点：老实现 vs 新实现

### 3.1 Q1 墙钟↔媒体映射：从"假设相等"到"逐段声明"

| | 实现 |
|---|---|
| **老** | 不存在映射。前端 `abs_ms = W0 + currentTime×1000`（[`index.html:572`](../../app/static/lab/index.html#L572)）；`clip_builder` `offset = abs_ms − 首选中段 ts`（[`clip_builder.py:297`](../../app/services/lab/clip_builder.py#L297)）。两处都是"媒体秒数 ≡ 墙钟秒数"的恒等代入 |
| **新** | 写侧每段多一行 `#EXT-X-PROGRAM-DATE-TIME:{段首帧墙钟}`；前端从 hls.js 的 `levels[].details.fragments`（每项带 `programDateTime` / `start` / `duration`）拿到完整分段映射；后端用清单的 `(ts_us, EXTINF)` 逐行表 + `.idx` 自己算 |

#### 选型：四个方案只差一件事——映射放在哪

| 方案 | 映射载体 | 代价 / 影响面 | 结论 |
|---|---|---|---|
| **A** 轴不动 + 逐段 PDT | HLS 原生字段，播放器直接解析 | 写侧每段多一行文本；`VodEntry` 加一个可选字段；前端与 `clip_builder` 各自改换算。**不动落盘二进制、不动 tfdt、不新增接口** | **采用** |
| B 轴改墙钟（`tfdt = 段墙钟 − step 起点`），gap 留洞 | 不需要映射，两轴合一 | MSE `buffered` 出现空洞，hls.js 播到洞口停摆、不自己跨（[HLS_TIMELINE_PITFALL.md](../archive/resolved_issues/HLS_TIMELINE_PITFALL.md) 记录的原坑）；**且同一份字节在 ffmpeg 侧给的是另一条时间轴**——洞 ≤10 s 保留、>10 s 静默抹平（§4 案例 3a–3f），导出的 mp4 与回放对不上，分界线藏在 ffmpeg 默认值里 | 否：已踩过，且新增一条跨消费者不一致 |
| C 轴改墙钟 + 造填充段补洞（黑屏帧） | 同上，且连续 | 两轴合一后**所有换算变成恒等式**，前端 / `clip_builder` / timeline 全不用改。但**导出成片与送标 clip 里会混入不存在的画面** | 否：**不往证据里写不存在的画面**。空洞改在墙钟轴与 UI 上表达（§3.4） |
| D 轴不动 + `/timeline` 增 `media_spans` 映射表（0908 原拟） | 自研 JSON 侧信道 | 不动落盘、不动播放器；但映射信息 playlist 里本就有，JSON 是它的复制品 → 两处真源可能不一致；前端仍要自己实现分段查找 | 否：见下 |

**A 优于 D 的三条**：

1. **不新增真源。** 段墙钟 + 逐段 EXTINF 本就是完整的分段映射，playlist 逐段各占一行，
   PDT 只是把已有的那个数写成播放器认识的形式；D 是把同一份信息再拷进 JSON。
2. **前端不用自己建表。** hls.js 解析后 `fragments[]` 每项自带 `programDateTime` / `start` /
   `duration`（本仓库自带的 `app/static/lab/vendor/hls.js` 里两个符号都在，**API 形态待接入
   时核验**）。D 要多一次 HTTP、多一套前端查找逻辑。
3. **对 ffmpeg 零风险**（§4 案例 P 实测逐帧与基线相同），导出与裁剪两条链路不受牵连。

#### PDT 到底给谁用

| | 有用吗 | 说明 |
|---|---|---|
| 前端建墙钟↔媒体映射 | **是，这是唯一目的** | 标记落点、打点上报、点击跳转全用它 |
| 让空洞在回放里可见 | **是，且是硬需求** | 判据是「相邻两段 PDT 差 ≫ 前一段 EXTINF」——**依赖 Q2 先修好**，否则差值算出来 ≈0 |
| 显示"这一帧是几点拍的" | 是 | 今天页面上那个 `abs_ms` 是假墙钟 |
| 修 `clip_builder` | **否** | ffmpeg 不读 PDT（§4 实测）。后端换算只能在 Python 侧用 EXTINF 累加自己算 |
| 影响导出 / 裁剪产物 | **否** | 这正是它可以安全加进清单的原因 |

#### 必须逐段写，只写首段等于白写

HLS 允许只在首段声明、后续由播放器按 EXTINF 累加推导；而我们的媒体轴是压紧的，累加推出来
的正是"没有任何空隙"的那条轴——**推导结果会精确地把 gap 抹掉，反过来宣称从没断过流**。
逐段写才是在每个段上重新锚一次。这一条写错不会报错、不会出画面问题，只会让整套换算静默
退回今天的错误状态。

#### 换算式是恒等式，不是插值

```text
目标墙钟 t
  → 段 i    = 清单里最后一个 ts_us ≤ t              （bisect_right − 1）
  → 帧号 k  = searchsorted(sidecar_i, t)            （raw 轨才有 .idx）
  → 媒体秒  = Σ_{j<i} EXTINF_j  +  k × EXTINF_i / N_i
```

段内那一项是**精确**的：cv2 以 `eff_fps` 写 N 帧，第 k 帧的媒体时刻恰为 `k / eff_fps`，
而 `EXTINF = N / eff_fps`，故 `k / eff_fps ≡ k × EXTINF / N`。**精确性不依赖采集匀速，
只依赖"cv2 等间隔写帧"**——有 `.idx` 的 raw 轨在任何抖动/断流下都精确。

> **`bisect_right − 1` 的方向不能反**：索引里存的是**段起始** ts，查询问的是"哪个段包含
> 这个 ts"。`left` 取到的是该 ts **之后**那个段；且 `ts_us = int(ts*1e6)` 是截断值，连
> "ts 恰为该段首帧"这种可能侥幸的情形也被堵死，用错方向是无条件错。

拿不到这份精确的有两处，都因为手上没有 `.idx`：

| 谁 | 段内怎么办 | 正常段误差 | 跨 gap 段误差 |
| --- | --- | --- | --- |
| processed 轨（有意不产 `.idx`） | 按比例插值 | ≤ 一帧 | **最大 ≈ gap（~20 s）** |
| 前端（浏览器侧只有 PDT + EXTINF） | 按比例插值 | ≤ 一帧 | **最大 ≈ gap（~20 s）** |

前端那一行是要命的：**打点上报的 `abs_ms` 由它算出**，后端再精确也救不回一个算错的入参。
这是 Q2 必须先修的第二个理由。

### 3.2 Q2 空洞被段吞掉：从"计数切段"到"进重连先 flush"

**这一条反直觉，且决定了其余所有结论的形状。**

| | 实现 |
|---|---|
| **老** | 切段是纯计数切：`SegmentSweeper` 只拉**攒满 `ca_segment_len`（300 帧）的整段**，不足一段的残帧只在**拆除**时由 [`flush_residual`](../../app/services/recording/service.py#L185) 收尾。而重连不拆除——`_exit_reconnect_mode(cleanup=False)` 不清队列、不 flush（[`manager.py:295`](../../app/services/health_monitor/manager.py#L295)）。断流那一刻攒在 CA 队列里的半批帧**留在原地，被重连后的帧补满**，拼成一个横跨 gap 的段 |
| **新** | `_enter_reconnect_mode` 判定断流时调一次 `recording_service.flush_residual(cq)`，把断流前那半批帧单独切成一个短段；空洞落到段边界 |

拿 [`_encode`](../../app/storage/hls/_encode.py) 的真代码跑（`raw_fps=30`、段长 300 帧、
gap = 20 s）：

```text
断流前已攒   eff_fps    EXTINF     真实内容    慢放     墙钟跨度
──────────────────────────────────────────────────────────────
    1 帧      9.99      30.03s     10.00s    3.00x    29.93s
   75 帧      9.99      30.03s     10.00s    3.00x    29.93s
  150 帧      9.99      30.03s     10.00s    3.00x    29.93s
  299 帧      9.99      30.03s     10.00s    3.00x    29.93s
──────────────────────────────────────────────────────────────
  无断流      30.00     10.00s     10.00s    1.00x     9.97s
```

**"断流前已攒了多少帧"完全不影响结果**——`eff_fps` 只看首末帧跨度，而跨度恒为
「10 s 内容 + 20 s gap」。该段 `eff_fps` 从 30 掉到 9.99（仍在 `[1,60]` 合理带内，
**不触发退化兜底**），cv2 就按 9.99 fps 把 300 帧写下去：**10 秒的真实画面被拉成 30 秒慢放。**

两个推论决定了 Q1 / Q4 的可行性：

- **`EXTINF(30.03 s) ≈ 墙钟跨度(29.93 s)`，差 0.1 s。** gap 被这一段吸收，**段边界处两轴
  仍然对齐**——`gap_i` 算出来是 0.1 s，不是 20 s。**这不是公式错**：那一段的 EXTINF 确实
  覆盖了它的墙钟跨度；失真跑到了段**内部**（该段不匀速）。
- 所以 §1.2 闭式解里那个 `G`，**只在 gap 恰好落在段边界时才累积**；默认路径下它被吸收进
  段内部，换成了另一种失真。

#### 决策与原因

| 决策 | 原因 |
|---|---|
| **必须在进入重连时 flush，不能在重连成功时 flush** | 成功判定的依据就是"已经来了新帧"，那时残批里已混进重连后的帧，段仍横跨 gap（只是被吞的比例变了），慢放照旧 |
| **走 `RecordingService` 的提交队列，不绕过** | `drain_ca_raw` 与 sweeper 的 `take_raw_segment` 同走 `_raw_lock`，并发安全；但段的**顺序**靠同一条 `SerialTaskQueue` 构造，绕过就可能乱序 → tfdt 碰撞 |
| 为什么必须先落它 | 它是 Q1（PDT 才画得出断口）与 Q4（`gap_i` 才是真值）的共同前提 |

**代价**：每次重连多落一个不足 300 帧的短段——合法 HLS 段，无特殊处理。极端情况是流在抖动
（反复死/活），会连出若干短段；其中只有 1 帧的段会撞上退化兜底（`eff_fps` 回落 15.0、
`EXTINF = 0.067 s`），仍自洽、不出洞，见 §7。

**收益**（三件事一起走）：慢放消失（缺陷 #4）；gap 回到段边界，PDT 与 `gap_i` 都给出真值；
每段恢复匀速，前端按比例插值自动精确（打点往返自洽）。

### 3.3 Q3 段查询两个真源：从"文件系统 ∩ 清单"到"清单唯一"

| | 实现 |
|---|---|
| **老** | 文件系统答"段在不在"，清单答"登记没登记"，读侧逐个函数记住哪个含在途段——[`_read.py`](../../app/storage/hls/_read.py) 与 [`_layout.py`](../../app/storage/hls/_layout.py) 各挂着一条 ⚠ 注释提醒这件事。`clip_builder` 用文件系统枚举，会把未登记段写进临时清单喂 ffmpeg |
| **新** | 纯清单解析：逐条目 `parse_segment_name(URI)` 得 `ts_us`，配同条目的 EXTINF。`_layout.list_segments*` 降级为域内私有 `_scan_segment_files`，只服务删除与自检，并从 `__all__` 摘掉 |

#### 决策原因三条

1. **一个真源。** 那两条 ⚠ 注释就是这份认知负担的证据。
2. **直接修掉一整类静默失败。** 喂未登记段给 ffmpeg 命中的是
   [DESIGN_SEGMENT_CONCAT.md](../kb/DESIGN_SEGMENT_CONCAT.md) §5.3：exit 0、任何日志级别都
   无输出、`-xerror` 抓不住，产出结构完整、ffprobe 满意、能正常播放、但少了一截的 mp4。
   **判据从"文件在不在"换成"条目在不在"，这类失败在入口就没了。**
3. **定位的权威源从"两个文件 join"塌成"清单的一行"**：

```text
#EXT-X-PROGRAM-DATE-TIME:2026-09-19T12:00:00.000Z   ← 方案 A 新增：该段首帧墙钟
#EXTINF:10.013,                                      ← 该段媒体长度
raw_segment_1700000000000000.mp4                     ← 文件名里的 ts_us 就是墙钟锚点
```

**一行条目同时给出墙钟锚点与媒体长度，无需 join。** 收口的是**枚举入口**不是命名：ts 仍从
URI 行解析（[`parse_segment_name`](../../app/storage/hls/_layout.py) 已有），`.idx` sidecar
照样靠同名配对。两条派生量全在清单里：

```text
tfdt  = Σ 前面各段的 EXTINF                                      ← 写侧算，读侧不用
gap_i = seg_{i+1}.ts_us − (seg_i.ts_us + EXTINF_i × 1e6)        ← 断流空隙
```

#### 代价，已知并接受

| 代价 | 说明 |
|---|---|
| 未登记段的帧对离线反查不可达 | 成因只有两种：`_m3u8.append` 抛 `OSError`，或进程崩在 `os.replace(段)` 与 append 之间。**这些文件本身是完整可解的 fMP4**（stage-then-replace 之后域目录里不会出现 mp4v 半成品），只是没登记。概率低、路径本就异常，换一致性 |
| 404 / 503 两档诊断塌成一档 | [`traceback.py:201`](../../app/routers/traceback.py#L201) 与 [`step_exporter.py:113`](../../app/services/lab/step_exporter.py#L113) 今天靠"盘上有段 vs 清单有条目"分出「挑错 track」和「首段还在转码，再等等」。收口后两者都表现为"清单不存在"，分不开 |

#### 顺带：收口比现状快 32 倍

实测（Windows，540 项的 step 目录 = 180 段 × 双轨 + sidecar，180 条 playlist）：

```text
读 m3u8 + 解析                       0.216 ms/次     ← 收口后的唯一路径
os.scandir + is_file + 正则          0.432 ms/次
Path.iterdir + is_file + 正则        6.925 ms/次     ← 现役 _layout.list_segments_by_track
内存 bisect 单次段级定位              0.0001 ms/次     ← 定位本身不是成本
```

差距里大部分是 `Path.is_file()` 对 540 个目录项各发一次 stat。**这是收口的副产品不是理由**
——理由是上面三条；但它确实顺手把 `clip_builder` 一次构建的两次全目录遍历（`_select_segments`
与 `_validate_continuity`，合计 ~13 ms）换成一次清单解析。

### 3.4 Q4 空洞的表达：从"静默粘合"到"墙钟轴上的禁区 + 拒绝出片"

| | 实现 |
|---|---|
| **老** | 空洞在任何地方都不可见：回放里被粘合成连续视频，导出/裁剪把跨空洞内容拼成一个声称连续的 mp4，`_validate_continuity` 的容差还会主动放行 |
| **新** | 媒体轴上宽度仍为零（**不造填充段、不写黑屏帧、不改 tfdt**）；墙钟轴上由 `gap_i` 画成一块不可选中的禁区；**任何跨越空洞的区间都不产出成片** |

#### 决策 1：不造填充帧（否掉方案 C）

C 能让所有换算变成恒等式、前端与后端全不用改——代价是**导出成片与送标 clip 里混入不存在的
画面**。这些产物的去向是标注样本与汇报素材，**不往证据里写不存在的画面**。

#### 决策 2：进度条横轴必须是墙钟

压紧的媒体轴上空洞宽度为零，画不出"一段"；只有铺在墙钟轴上，那 20 秒才占得到位置。

#### 决策 3：跨空洞一律拒绝，裁剪与整段导出同档（已拍板）

理由是语义而非实现——一份声称覆盖 `[t1, t2]` 的录像，中间少了 20 秒还接在一起，就是在撒谎。
不按断言强度分档，因为两类产物都会流向汇报与标注。

| 谁 | 怎么执行 |
|---|---|
| 前端 | 选区跨禁区时按钮置灰，不让提交 |
| [`clip_builder._validate_continuity`](../../app/services/lab/clip_builder.py#L259) | `gap_i > 0` 即拒绝，报出确切空洞区间与时长（见 Q7） |
| [`step_exporter.export`](../../app/services/lab/step_exporter.py#L95) | step 内含空洞 → 拒绝，新增一档 `StepExportHasGaps`，错误体带空洞清单 |
| 前端下载按钮 | 该 step 含空洞时置灰，提示"本段含 N 处信号中断，不可导出" |
| 后端兜底 | 前端置灰只是体验，**服务端必须独立拒绝**——API 可以被直接调 |

> **代价说清楚**：一个 10 分钟的 step 只要断过一次流，整段原片就取不到了。拿不到的是
> **成片**，不是数据——段、`.idx`、features 全在盘上，离线反查照常工作。
>
> 若日后确实需要取原片，**放宽的方向是"按空洞切成多个文件"**（每个文件内部连续、文件名带
> 各自的墙钟区间），而不是放行一个跨空洞的单文件。这条留作后续，本次不做。

#### 为什么不用 `#EXT-X-DISCONTINUITY`

它表达的是"编码参数变了"（timescale / codec / PTS 基准重置），不是时间空白——断流前后编码
参数没变，写它会误导播放器。将来换轨或换编码参数时才是它的场景。

## 4. 决策所依赖的实测：对 ffmpeg 而言 EXTINF 是装饰，tfdt 是承重

材料刻意让两者错开（这正是 [DESIGN_SEGMENT_CONCAT.md](../kb/DESIGN_SEGMENT_CONCAT.md) §5
留的待核验项所要求的，仓库原有材料两者天然一致、区分不了）：3 个 fMP4 fragment，各 20 帧
@10fps = 2.000 s 媒体时长，timescale 90000，共用一份 init。**每帧是一块纯灰，灰度值编码它的
全局帧号**——解出来的画面能反查"这是源里第几帧"，从而判定 seek 落点，而不只是看时长。

```text
#    tfdt(媒体轴落点)     EXTINF(清单声明)   命令              产物                      判定
────────────────────────────────────────────────────────────────────────────────────────────
1    0 / 2 / 4 s          2.0 × 3            -c copy           6.000s、60 帧、源帧 0–59   基线
2    0 / 2 / 4 s          3.0 × 3（虚高）     -c copy           6.000s、60 帧、源帧 0–59   与基线逐帧相同
8    0 / 2 / 4 s          0.1 × 3（荒谬小）   -c copy           6.000s、60 帧、源帧 0–59   与基线逐帧相同
P    0 / 2 / 4 s          2.0 × 3 **+ PDT**  -c copy           6.000s、60 帧、源帧 0–59   与基线逐帧相同
────────────────────────────────────────────────────────────────────────────────────────────
4    0 / 2 / 4 s          3.0 × 3（虚高）     -ss 3.0（输出侧） 首帧 = 源帧 30             听 tfdt
4b   0 / 2 / 4 s          2.0 × 3（真值）     -ss 3.0（输出侧） 首帧 = 源帧 30             与 4 相同
────────────────────────────────────────────────────────────────────────────────────────────
5    子集 2 / 4 s         2.0 × 2            -ss 0.5           首帧 = 源帧 25             首段归一到 0
6    子集 100 / 102 s     2.0 × 2            -ss 0.5           首帧 = 源帧 25             与 5 相同
7    子集 100 / 102 s     2.0 × 2            -c copy           start_time=0、4.000s       绝对 tfdt 被归零
────────────────────────────────────────────────────────────────────────────────── 洞的阈值 ──
3a   0 / 3 / 6 s（洞 1s） 2.0 × 3            -c copy           8.000s、包仍 60、解码 80 帧 洞保留，冻结上一帧
3b   0 / 7 / 14 s（洞 5s）2.0 × 3            -c copy           16.000s                    洞保留
3c   0 / 11 / 22 s（洞 9s）2.0 × 3           -c copy           24.000s                    洞保留
3d   0 / 17 / 34 s（洞 15s）2.0 × 3          -c copy           6.000s ☠️                  洞被**静默抹平**
3e   同 3d                2.0 × 3            -dts_delta_threshold 20  36.000s             洞又保留了
3f   同 3b（洞 5s）        2.0 × 3            -dts_delta_threshold 2   6.000s              洞被抹平
────────────────────────────────────────────────────────────────────────────────────────────
```

四条结论，各自判了哪个方案：

| 实测结论 | 用在哪 |
|---|---|
| **ffmpeg 的时间轴完全来自 `tfdt` + sample duration，EXTINF 写成什么都不影响产物**（案例 2 与 8：虚高 50%、缩到 1/20，逐帧产物与基线相同） | 判了 Q6：`clip_builder` 的墙钟 EXTINF 是空操作 |
| **子集的首段 tfdt 被归一到 0**（案例 6/7：100 s 的绝对落点照样得到 `start_time=0`） | `-ss` 是"相对首个选中段的媒体起点"；tfdt 不可用于定位（§2.4） |
| **`EXT-X-PROGRAM-DATE-TIME` 对 ffmpeg 是明示无效的**（案例 P） | 方案 A 对 ffmpeg 零风险；同时说明 PDT 修不了 `clip_builder` |
| **段间空洞只在 10 秒以内会被保留，超过就被静默抹平**（案例 3a–3f），机制是 `-dts_delta_threshold`（默认 10 s） | 判了方案 B/C 的死刑 |

### PDT 对 ffmpeg 无效，且是明示的

不用推断，`-loglevel info` 直接把它打出来，一段一行：

```text
[hls @ ...] Skip ('#EXT-X-PROGRAM-DATE-TIME:2026-09-19T12:00:00.000Z')
[hls @ ...] Skip ('#EXT-X-PROGRAM-DATE-TIME:2026-09-19T12:00:02.000Z')
[hls @ ...] Skip ('#EXT-X-PROGRAM-DATE-TIME:2026-09-19T12:00:32.000Z')
```

`ffprobe -show_format -show_streams` 的 tag 里也没有它的任何痕迹。**ffmpeg 既不用它、也不
透出它**——所以 PDT 对 `step_exporter` / `clip_builder` 两条链路是纯粹的零影响。
推论：**墙钟映射不可能经 PDT 传给 ffmpeg**，后端要的 wall→media 换算只能在 Python 侧用
清单的 EXTINF 累加算出来，再把算好的秒数交给 `-ss`。

### 段间空洞的 10 秒阈值

洞开到 1 / 5 / 9 秒，ffmpeg 老老实实保留（时长被撑到 8 / 16 / 24 s）；开到 15 秒，**产物直接
缩回 6.000 s，洞没了，exit 0、无警告**。加 `-dts_delta_threshold 20` 洞就回来了，把阈值压到
2 洞又没了——确认是 `dts_delta_threshold` 在判：**跳变大于阈值按"不连续"处理、重基时间戳；
小于阈值当真实空洞保留。**

对本次选型是决定性的：**若把 tfdt 改成墙钟（方案 B/C），同一份字节在两类消费者手里会给出
两条不同的时间轴**——浏览器按洞停摆，而 ffmpeg 导出时短洞保留、长洞抹平，导出的 mp4 与
回放看到的对不上，且分界线是一个藏在 ffmpeg 默认值里的 10 秒。

> **EXTINF 只是对 ffmpeg 无效，对播放器仍然承重**：`<video>.duration`、seek 选段、缓冲与
> TARGETDURATION 判断都吃它，写错会出段尾 MSE 缓冲洞与总时长缩水。**不要据此放松写侧
> EXTINF 的正确性**，本节说的只是"ffmpeg 消费端不看它"。

## 6. 复现方法

探针脚本 `probe.py`（stdlib + 仓库自带 ffmpeg，不依赖 app 包）留在
`E:/tmp/timebase_probe/`，**不入库**——它造的材料是一次性的。要重做：

```bash
# 造材料：3 段 × 20 帧 @10fps，每帧纯灰、灰度 = 8 + 4×全局帧号，timescale 90000，共用 init
"$FF" -framerate 10 -start_number {0|20|40} -i f%03d.pgm -frames:v 20 \
  -c:v libx264 -preset veryfast -crf 18 -pix_fmt yuv420p -an \
  -hls_segment_type fmp4 -hls_segment_options video_track_timescale=90000 \
  -hls_fmp4_init_filename init.mp4 -hls_segment_filename 'fragment_%d.mp4' \
  -start_number 0 -hls_time 99999 -hls_list_size 0 -f hls index.m3u8

# 改 tfdt：复用 app/storage/hls/_fmp4.py 的 box 遍历（moof→traf→tfdt，v1 是 64-bit）
# 手写清单：EXTINF 取要验的值，#EXT-X-MAP:URI="init.mp4"，带 #EXT-X-ENDLIST
"$FF" -y -allowed_extensions ALL -i probe.m3u8 [-ss X -to Y] -c copy out.mp4

# 判读落点：解成灰度裸流，取每帧中心像素 → 反查全局帧号
"$FF" -v error -i out.mp4 -f rawvideo -pix_fmt gray - | <取第 k 帧中心字节，(px-8)/4 即源帧号>

# PDT 被跳过（案例 P）：清单里加 #EXT-X-PROGRAM-DATE-TIME 行，看 demuxer 自己说
"$FF" -allowed_extensions ALL -i pdt.m3u8 -f null - 2>&1 | grep "Skip"
#   → [hls @ ...] Skip ('#EXT-X-PROGRAM-DATE-TIME:...')   一段一行

# 空洞阈值（案例 3a–3f）：tfdt 拉开 N 秒，看产物时长是被撑开还是缩回 6.000
#   洞 1/5/9s → 8/16/24s（保留）；洞 15s → 6.000s（抹平）
"$FF" -y -allowed_extensions ALL -dts_delta_threshold 20 -i probe.m3u8 -c copy out.mp4
#   → 洞 15s 加了这个参数就变 36.000s，确认是 dts_delta_threshold 在判
```

> **测材料有状态，逐例都要重打 tfdt。** 本次初稿的案例 P 就是在上一例遗留的
> tfdt（0/100/102 s）上跑的——结论碰巧没变（PDT 确实无影响），但那次的 6.000 s 是
> ffmpeg 触发了 10 秒阈值把 98 秒跳变重基**凑**出来的，不是基线。已用干净材料重测。
