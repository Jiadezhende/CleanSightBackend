# `/algorithm` — 算法类纯计算接口

图进、结论出。这组端点**不读库、不写盘、不发告警、无任何持久化**，同一张图打多少次结果都一样。

与 `/lab-f3m8`（送标数据飞轮）没有关系：那组要挑任务、剪视频、传 Label Studio；这组只是把一张图喂给算法。

- 通用约定（Base URL / Gateway / 错误模型）见 [README](README.md)。Gateway 落**普通档**（默认 60 次/60 s）。
- 无鉴权。前缀不含混淆串。

---

## POST /algorithm/colorstrip

**用途**：操作员拍一张「瓶身参考色卡 + 待测试纸」的照片，前端把图转成 base64 发过来，后端返回这条试纸**合格 / 不合格**；判不出来时返回该怎么补拍。

用于过氧乙酸消毒液试纸。做的是**相对比色**——以色卡上 2000 刻度块为参考下限，试纸比它更深即合格。之所以要求色卡和试纸在同一张图里，是因为同一帧共享光照与白平衡，误差在两者相减时大部分抵消；分两张拍就得标定色温和曝光，现场做不到。

**拍照要求（前端最好在取景框里提示）**：

| 要求 | 说明 |
|------|------|
| 色卡**两块**都要入镜 | 800 与 2000 两个刻度块。只拍 2000 那一块会被拒判——算法没办法确认那块到底是不是参考 |
| 画面里只有 **1 条**试纸 | 多了会被当成混入异物而拒判 |
| 试纸要已显色 | 未显色的垫是浅白色，根本进不了检测，会按"试纸不在画面里"拒判 |
| 别让反光/瓶身弧面挡住色块 | 挡掉一部分会导致"两块不等大"而认不出色卡 |

**不要求**的：色卡与试纸谁左谁右、谁上谁下、整图转 90°/180° 都不影响判定（8 张真实样本 × 5 种姿态实测结论一致）。

**查询参数**：

| 参数 | 类型 | 必填 | 默认 | 说明 |
|------|------|------|------|------|
| `profile` | string | 否 | `default` | 参数档名。换光照场景（钨丝灯/荧光灯）时才需要动；档名列表在 `app/services/algorithm/colorstrip/params.yaml`，写了不存在的档 → **400**。**常规调用不要传这个参数** |

**请求体** `ColorstripRequest`：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `image_base64` | string | 是 | 图片 base64。裸 base64 与 data URL（`data:image/jpeg;base64,...`）**都收**——`FileReader.readAsDataURL` 直出的就是后者，不必自己剥前缀。串里的换行会被忽略 |

图片大小上限 **12 MB**（base64 **解码后**的字节数，手机直出照片通常 3–5 MB）。超限 → 400。

### 响应 `200` `ColorstripResponse`

四个平铺字段，无嵌套、无数组。**算法判不出来时也是 200**（见「错误」一节）。

```jsonc
// 判出来了，合格
{ "ok": true,  "passed": true,  "code": "OK", "message": "合格：试纸比参考色深" }

// 判出来了，不合格
{ "ok": true,  "passed": false, "code": "OK", "message": "不合格：试纸比参考色浅" }

// 判不出来
{
  "ok": false,
  "passed": null,
  "code": "E_NO_CARD",
  "message": "未找到色卡：完整色卡两块（800 与 2000）都要入镜，别被反光或瓶身弧面挡住"
}
```

| 字段 | 类型 | 说明（含 null 条件） |
|------|------|---------------------|
| `ok` | bool | 判定是否成立 |
| `passed` | bool \| null | 合格与否。**`ok=false` 时恒 null** |
| `code` | string | 见下表 |
| `message` | string | 中文一句话，可直接展示给操作员。`ok=true` 时是结论，`ok=false` 时是「现象 + 该怎么办」 |

**`code` 取值**：

| `code` | `ok` | 含义 | 操作员该做什么 |
|--------|------|------|---------------|
| `OK` | true | 判定成立，看 `passed` | — |
| `E_TOO_FEW_PATCHES` | false | 画面里没有可比的色块 | 确认色卡和试纸都拍进去了，别太远、别过曝 |
| `E_NO_CARD` | false | 找不到色卡，参考下限无从确定 | 完整色卡两块都要入镜，别被反光或瓶身弧面挡住 |
| `E_CARD_AMBIGUOUS` | false | 有多组疑似色卡，参考下限有歧义 | 移走画面里其他红橙色物体 |
| `E_STRIP_COUNT` | false | 待测试纸数量不是 1 | 确认试纸已显色，画面里只留 1 条 |

> `message` 里的文案就是上表最后一列，可以直接用；要自己做多语言或改措辞就按 `code` 分支。

### 错误

| 状态 | 触发条件 | 响应体形态 |
|------|---------|-----------|
| `400` | `image_base64` 为空 / 不是合法 base64 / data URL 缺 `;base64,` 分隔符 / 解码后不是图片 / 超过 12 MB | `{"error":"Validation error","detail":"...","field":"image_base64"}` |
| `400` | `profile` 写了不存在的档 | `{"error":"Validation error","detail":"配置里没有档 'xxx'；现有档: default, low_res, warm_light","field":"profile"}` |
| `422` | 请求体缺 `image_base64` 字段、JSON 格式错 | FastAPI 标准校验体（`detail` 是数组），与上面两种**形态不同** |
| `429` | 触发 Gateway 普通档限流（默认 60 次/60 s） | 见 [README](README.md) |

**400 与 200+`ok:false` 的分工是本端点最要紧的一条**：

- **400 = 请求本身有问题**（base64 发错了、图太大），重发同样的请求没有意义。
- **200 + `ok:false` = 请求没问题，是照片拍得不对**，让用户重拍一张再调一次就行。

判分支只认 status code 与 `ok`，别依赖 body 字段形态——422 的 body 和 400 的 body 不一样。

### 前端坑点

- **`ok=false` 不等于不合格。** `if (!resp.passed) 显示"不合格"` 是错的：判不出来时 `passed` 是 `null`，会被当成假值。正确写法是先看 `ok`：

  ```js
  if (res.ok) showVerdict(res.passed);   // 合格 / 不合格
  else        showRetry(res.message);    // 让用户按 message 重拍
  ```

- **别把拒判当报错弹窗。** `ok=false` 是正常业务态（用户拍糊了），应引导重拍，不是"系统出错了"。
- **传 data URL 不用剥前缀**，但别传成 `URL.createObjectURL()` 的 blob URL——那不是 base64。
- **单次请求约 0.1 s**（4.6 MB 图实测解码 55 ms + 判定 23 ms），别做成 onChange 实时触发，按钮点一次调一次即可。
- **不要传 `?profile=`**，除非现场换了光源并且后端已经为那个场景标定过参数档。传错档名直接 400；传了个没标定的档，结果可信度无从保证。
- **响应里没有测量值**（L\*、裕度、色相、色块坐标、标注效果图都没有）。需要这些请找后端：拒判时的完整判据诊断在服务端日志里，调参用 `python -m app.services.algorithm.colorstrip.cli`。

### 静默失败

| 现象 | 后端实际状态 |
|------|-------------|
| 一直返回 `E_STRIP_COUNT`，可用户明明拍了试纸 | 试纸**未显色**。未显色的垫是浅白色，进不了红橙色检测，后端看到的就是"画面里没有试纸"。这道计数门禁是刻意的：没有它，浓度越低的样本越容易被静默丢掉——方向正好反了 |
| 一直返回 `E_NO_CARD`，可色卡明明在画面里 | 多半只拍到了 2000 一块，或者 800 那块被反光/瓶身弧面啃掉了一部分。两块必须都完整可见 |
| 同一条试纸、同一张图，换 `?profile=` 结论变了 | 正常。不同参数档是为不同光照场景标定的，别混用；常规调用不传这个参数 |
| 返回 `ok=true`、`passed=true`，但操作员肉眼觉得偏淡 | **本算法在临界区（接近 2000 刻度）没有真实样本验证过**，裕度很小时结论不可信。它的定位是防误操作与留痕，不是精密定量 |

> 还有一条安全边界要知道：本接口**不防蓄意伪造**。画面里若完全没有真色卡、却有两块红橙色物体恰好凑齐色卡的结构与色值，算法会把它当色卡并给出判定。防造假该由拍摄时间戳、随机水印、现场抽查等业务手段承担，不是比色算法的职责。
