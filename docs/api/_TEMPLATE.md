# API 文档写作规范 + 模板

本文件规定 `docs/api/*.md` 怎么写。目标读者是**对接前端**，不是熟悉后端的人。
下半部是可直接复制的骨架。

> 全局通用约定（Base URL、Gateway、错误模型、时间戳单位、枚举）集中在 [README.md](README.md)，**各 router 文件不重复**，只在字段旁按需复述关键单位。

---

## 一、写作规范（六条硬原则）

1. **站在前端任务视角，不是后端契约视角。**
   不要只罗列"我返回哪些字段"。要回答前端的真实问题：*我要做 X，该调哪个、怎么调、拿到的东西怎么用、异常怎么办。* 每个端点开头一句话说清"前端用它来干什么"。

2. **每个可能为 `null` / 缺省 / 空的字段，必须写清出现条件。**
   "`source_ip` string | null" 不够——要写"DB 不可用或表中无此任务时为 null"。前端据此决定要不要兜底。

3. **判分支只认 HTTP status code，不依赖响应体字段——文档要主动点破不一致。**
   同一端点不同错误的响应体形态可能不同（有的带 `error`/`resource_type`，有的只有 `detail`）。凡有此情况，显式写一句"两种 XXX 的 body 字段不一致，别依赖 body 判断"。

4. **时间戳单位在字段旁复述，不让读者翻 README。**
   秒 / 毫秒 / 微秒在本系统混用（`/admin` 用秒，告警/traceback 用毫秒，段用微秒），是高频踩坑点。每个时间字段后缀单位，如 `detected_at`（epoch **毫秒**，可为 null）。

5. **"静默失败"必须单列。**
   凡后端**不报错、只是没数据**的情况（返回 200 空数组 / 降级 / WS 静默），前端会误判为 bug。端点末尾用一张「现象 → 后端实际状态」对照表兜住。

6. **能指就指参考实现。**
   仓库内若有消费该端点的代码（如 [app/static/lab/index.html](../../app/static/lab/index.html) 的 `attachVideo`），在文末链过去——比任何文字都准。

> 契约以 `app/routers/*.py` 现码为准；字段变更同步改本目录对应文件。

## 二、每个端点必备的小节（缺一不可）

按下列顺序写，没有内容的小节可省，但**「错误」和「前端坑点/静默失败」不允许省**（哪怕写"无"）。

| 小节 | 写什么 | 常见漏写 |
|------|--------|---------|
| **用途** | 一句话，前端视角。数据来自内存还是 DB？实时还是历史？ | 只写端点名不写"拿它干嘛" |
| **请求** | path / query / body 每字段：类型、必填、默认值、取值范围/枚举。二选一/互斥关系写清 | 默认值、范围、非法值行为 |
| **成功响应** | 带注释的 jsonc **+** 字段表。数组元素结构、嵌套对象、每个可空字段的 null 条件 | null 条件、数组元素 schema |
| **错误** | 每个 status code 的触发条件 **+** 响应体形态。body 形态不一致要点破 | 只列 code 不列触发条件 |
| **前端坑点** | 分页/游标用法、推荐轮询频率、缓存头、边界情况、字段名与别处不一致 | 游标怎么用、轮询多快 |
| **静默失败** | 「现象 → 后端实际状态」对照表 | 整节漏写 |

## 三、模板骨架（复制这段开始写）

````markdown
# `/<prefix>` — <一句话定位>

<这组端点是干什么的；数据源（内存/DB/磁盘）；与别组的关系。通用约定见 [README](README.md)。>

<可选：多端点协作时画一张消费流程图，标清"谁出参数、谁吃参数">

```
  ① GET /list ──→ id ──→ ② WS /stream
```

---

## <METHOD> /<path>

<一句话：前端用它做什么。数据来自内存/DB/磁盘？实时/历史？>

**路径参数**：`id`（int）。
**查询参数**：

| 参数 | 类型 | 必填 | 默认 | 说明 |
|------|------|------|------|------|
| `since_seq` | int | 否 | 0 | 游标，只返回 `seq > since_seq` 的项；`<0` → **400** |

**请求体** `XxxRequest`（如有）：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `task_id` | int | 是 | 运行键 |

### 响应 `200`

```jsonc
{
  "total": 2,
  "items": [
    {
      "id": 123,
      "ts": 1751800000000,          // epoch 毫秒
      "source_ip": "192.168.0.10"   // DB 不可用时为 null —— null 条件写在字段表
    }
  ]
}
```

| 字段 | 类型 | 说明（含 null 条件） |
|------|------|---------------------|
| `total` | int | `items` 长度 |
| `items[].id` | int | → 下一步 `WS /stream?id=` |
| `items[].ts` | int | epoch **毫秒** |
| `items[].source_ip` | string \| null | DB 不可用或表中无此记录时为 **null** |

<排序规则、空结果形态（是否报错）、分页语义写这里。>

### 错误

| 状态 | 触发条件 | 响应体形态 |
|------|---------|-----------|
| `400` | `since_seq < 0` | `{"error":"...","detail":"...","field":"since_seq"}` |
| `404` | 资源不存在 | `{"error":"Resource not found","resource_type":"...","resource_id":"..."}` |
| `503` | DB 不可用 | `{"error":"...","retryable":true}` |

<若某端点"尽力而为、永不抛异常"，在此写明：总返回 200，部分失败用响应体字段表达。>
<若不同错误 body 形态不一致，点破："判分支只认 status code，别依赖 body 字段。">

### 前端坑点

- <游标用法：保存返回的 `max_seq`，下次以 `since_seq=max_seq` 请求，避免重复。>
- <推荐轮询频率：1–2 Hz。>
- <字段名与别处不一致：本端点用短名 `metric`/`level`，`/admin` 用全称 `alarm_type`/`alarm_level`。>
- <缓存头：`Cache-Control: private, max-age=60`。>

## 附：静默失败的几种情况

以下情况后端**不报错**，只是没有数据，排查时容易误判为 bug：

| 现象 | 后端实际状态 |
|------|------------|
| <WS 连上但一直无消息> | <当前无匹配 run，后端静默；查 `/list` 的 total 区分> |
| <拿到 200 但数组为空> | <资源已清理 vs 处理中——如何区分> |

<有参考实现就链：仓库内消费本接口的实现见 [xxx](../../app/static/xxx.html)。>
````
