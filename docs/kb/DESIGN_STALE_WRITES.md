# 迟到写入与换代冲突：防护设计

- **判据**：「前提检查 + 写」之间不穿插同资源的其他写，才算闭合（§2）。
- **工具**：单消费线程队列、锁（含锁内 CAS）、资源的原子操作原语。前两种要求写者同进程；跨进程只能用第三种，且对方的写也必须是原子的（§2）。
- **要点**：代次令牌写前比对或多版本（跨进程写者 / 路径跨代复用时优先多版本）；耗时任务执行与提交分离；每一代新建对象（§3）。
- **不算闭合**：门禁、在串行点外自查代次，最多缩小窗口；前提**单调**时门禁本身即闭合（§4）。
- **怎么选**见 §5；写错可重跑覆盖、无下游副作用的产物可以先不防。

锁清单、队列解耦、生命周期锁等基础设施见 [DESIGN_CONCURRENCY_AND_QUEUES.md](DESIGN_CONCURRENCY_AND_QUEUES.md)。

## 1. 同一资源的写交错，会让另一方的前提失效

追加、整体替换、删除目录、TTL 回收、注册表增删都是对同一资源的写，下文不区分。一次写是否正确，往往取决于它事先检查过的前提（「目录属于当前代」「目录还在」）；另一次写插进检查与写入之间，前提就可能不成立：

```text
写入方 A                              同一资源上的另一次写 B
  前提检查：目录属于当前代 ✓
                                      B：新一代首写时整域删除 / TTL rmtree
  写入                                ← 前提已不成立：旧数据串进新一代，或把删掉的目录重建成僵尸
```

## 2. 闭合竞态窗口只有三种工具

**闭合** = 无论以什么时序交错，同资源的其他写都插不进某次写的检查与写入之间；**缩窗** = 窗口变小但仍在（§4）。要闭合，同一资源上的所有写要么都经过同一个**串行点**（队列或锁）并在其内完成检查与写入，要么由资源的原子操作一步完成「检查 + 写」。两者内部统称**安全区**：只有安全区内的检查，才对紧随其后的写有效。

| 工具 | 适用 | 做法 | 本仓库例 | 边界 |
|------|------|------|----------|------|
| 单消费线程队列 | 同进程、单步很短的落盘写 | 同一资源的写都进同一条 `SerialTaskQueue`，提交序即执行序；不能加 worker | recording 的 hls / detections 队列（tfdt 按执行序累计） | 长任务堵队列（§3.2）；跨进程写者进不来 |
| 锁（含锁内 CAS） | 同进程的状态转换、注册表增删 | 比较和变更在同一临界区：「当前是 X 才改成 Y」 | `lock_for(task_id)` 内的 `stop_run(expected=cq)`；`_wlock` 内的 `remove_if` | 只管单个状态点，管不了多步流程 |
| 资源的原子操作原语 | 跨进程、写者没法共用串行点 | 由资源一步完成「检查 + 写」；与之冲突的写也须原子 | 写者只建域这一级目录，run 被回收后迟到写 `FileNotFoundError`；删除走 `utils.fs.remove` | 能检查什么由原语决定 |

原子原语的两个局限：

- **能检查的条件不等于真正的前提**：文件系统只能判断「目录在不在」，真正的前提往往是「目录属于某一代」，同一路径被新一代重建（ABA）时照样放行。文件系统没有 DB `UPDATE … WHERE version=?` 那样按版本号条件换名的原语。解法是路径不跨代复用（§3.1 多版本），或把提交放回属主串行点（§3.2）。
- **对方的写不是原子的**：`rmtree` 是复合写（列目录、逐个删、rmdir）。写入插在中途，结果是删了一半的目录里留着新文件；删除自己半途失败（Windows 上有文件被打开时），调用方若记成「删过了」接着写，新旧数据就混在一起。**解法：先 `rename` 到 `{root}/.trash/` 再对回收区 `rmtree`**。迟到的写要么随目录进回收区，要么碰到目录不存在而失败；rename 失败则目录原样未动，必须当成「没删」。回收区名字非数字，按数字名扫 step 的逻辑不会误认；rmtree 失败的留在回收区，下一轮再清。

## 3. 三个设计要点

### 3.1 代次令牌：写前比对，或多版本（MVCC）

**代次令牌**是标识「这次写属于哪一代」的值。两种用法都用它把不同代的写分开，差别在于在哪一侧分：

| 维度 | 写前比对 | 多版本（MVCC） |
|------|---------|---------------|
| 资源形态 | 各代共用一份（盘上同一路径） | 一代一个版本（盘上一代一个目录） |
| 令牌在哪里比 | 写者在安全区内比 | 读者按版本号选；写者只写自己那一版 |
| 换代动作 | 删除旧代，再写新代 | 新版本提交即生效，旧版本异步回收 |
| 迟到写入 | 必须进属主串行点比对，否则只能缩窗 | 写进旧版本，读者看不到 |
| 适用 | 写者都在同一进程、都走属主串行点 | 有跨进程写者、读写要锁定同一代，或路径跨代复用导致 ABA |

**令牌形态**：进程内用对象身份（`cq is current`；本仓库 `stop_run(expected=cq)`、`remove_if`、recording `_pending_flush` 条目带 cq 按身份核对）；跨进程 / 落盘用持久版本号。`(inode, size, mtime)` 这类内容戳只能说明「变没变」，说明不了「属于哪一代」，不能当令牌。

#### 用法一：写前比对

适用于写的前提由安全区之外的另一份资源决定。换代就是这种情况：「当前是哪一代」记在注册表里，控制面换代时属主队列并不知情，所以每个任务带上自己那一代的令牌，进队列后与注册表当前值比对。比对结果用于**授权删除**（只有当前代才能删整个目录，关乎正确性）和**丢弃旧代任务**（只为省开销）。本仓库落盘侧用多版本，写前比对只用在内存侧。

#### 用法二：多版本（MVCC）

各代写各自的版本目录，盘上互不相交，「哪一代生效」由读侧决定。规则：

1. **版本号在同一资源内严格单调、永不复用**：在同资源的串行点内按 `max(当前时间, 已有最大 + 1)` 分配。直接用墙钟的话，时钟回拨会让新版本不可见，还会被当成旧版本回收。分配者唯一且在同一串行点内时不加随机后缀（本仓库 `lock_for` 内的 `runs.allocate`，`run_id` 纯整数）；多个分配者无法共用串行点时，才用「时间前缀 + 随机后缀」，排序看前缀、身份比整串。版本号外露到 JSON / 前端时要落在 JS 安全整数（2^53）内（本仓库因此取毫秒而非 `time_ns`）。
2. **一代只分配一次版本号，各域共用**：跨域配对（录像与检测结果）比较版本号（本仓库：同一 run 目录下挂 `hls/` 与 `inference/`）。
3. **提交是原子的，空版本不能遮住上一代**。两种合法形态：
   - 原子 rename 提交：首份产物写进 `.{版本}.tmp/`，写完 rename 成 `{版本}/`；读者跳过点号开头的目录。
   - 可见判据提交：分配者直接建空版本目录，读侧只把「已有某个**原子出现**的主产物」的版本当作可见（本仓库：任一轨清单里有段，或 `detections.jsonl` 存在）。判据必须挑原子出现的标记，否则会选中半截版本。代价是存在「新版本先因快域可见」的窗口（本仓库的窗口见 [ARCHITECTURE_STORAGE_AND_SCHEMA.md](ARCHITECTURE_STORAGE_AND_SCHEMA.md)）。
4. **只有属主能建版本**：其余写者只写已存在的版本；版本被回收后，迟到写由文件系统原子失败，不会重建僵尸（本仓库：run 目录只由 `runs.allocate` 建，域写口只建域这一级）。
5. **读者只解析一次，此后只持句柄**：读写接口只收句柄（task, step, 版本）。「默认取最新」只能在唯一的解析口出现一次（本仓库 `runs.query(run_id=None)`）。跨多次请求的读（HLS 回放先取清单、再多次取段）把版本号带进 URL / token（本仓库 `run_id` 参数、MediaToken 的 `"r"` 键）。
6. **下游消费只接受输入已冻结的版本**。两种判法：
   - 封口标记：属主在一代最后一次写之后落 `SEALED`；进程重启时未封口的版本都已没有写者，统一补封。适用于消费方查不到写者注册表的场景。
   - 与写者注册表比对：注册表与消费方同进程时，「输入冻结」=「该版本不是当前活跃版本」（本仓库：离线提交时 `clients.get(task).run == run` → 409）。前提单调（§4），门禁即闭合。
7. **回收不能早于锁定读者**。两种做法：
   - 按版本 vacuum：只回收非最新且被取代超过宽限期的版本，宽限期大于最长的锁定读者。「非最新」一旦成立不会翻转，回收判断无需和写侧互斥。
   - 按容器整体 TTL：被取代的版本随上层容器留到 TTL，无需宽限期（本仓库按 step 整体 TTL）。前提是写者不建目录（规则 4）、删除原子（规则 8），且锁定读者在回收后拿到明确的「已回收」（404 / `reclaimed`），而不是半截数据。
8. **删除按 §2 的原子删除做**：先 rename 到回收区，失败按「没删」处理。
9. **一个文件只有一个写者**：多个 producer 各写各的文件，读侧合并；不在文件上做跨进程的「读回 → 合并 → 写回」。本仓库 `temporal.jsonl` 由离线 runner 读回-合并-写回，成立的前提是只有离线这一个写者；加第二个写者即违反本条。

与数据库 MVCC 逐条对应（txid ↔ 规则 1，已提交版本 ↔ 规则 3，快照读 ↔ 规则 5，vacuum ↔ 规则 7），一处不同：数据库的读者看「不晚于自己快照的最新版本」，这里的读者在解析那一刻看全局最新，之后锁定。

**前提只取决于同一串行点内的写时，不需要令牌**，靠顺序就够。例：同一 run 内相邻段的 tfdt 只取决于同一队列里的前序写，FIFO 即可。

### 3.2 耗时任务不进串行点：执行与提交分离

串行点一次只放行一个写，耗时任务放进去会堵住同一资源上的其他写。拆两段：**执行**放在安全区外；**提交**（比对令牌 + 写入）很短，放进资源属主的串行点，放不进去的用原子操作完成。采用多版本时提交不必进串行点：写者只写自己锁定的版本，与其他代盘上不相交（本仓库：recording 两条队列与离线子进程各写自己锁定的 run）。

### 3.3 每一代新建对象，不复用

新一代不复用上一代的对象再重置状态。迟到的写手里拿的是旧对象，最多写进旧对象自己，碰不到新一代。

- **内存侧**：每个 run 新建一个 CQ。CQ 的写门（非 ACTIVE 拒写）是免锁读、不原子，只负责拦住数据在旧对象里越积越多；真正起隔离作用的是「一代一个对象」。
- **落盘侧**：即 §3.1 的多版本。复用同一路径的只能靠写前比对加属主串行点兜住，跨进程写者还会留下 ABA 窗口。
- 只针对新旧两代争用同一资源；TTL 回收这类与代次无关的写不在其内。

## 4. 检查做在安全区外，最多缩小窗口

| 做法 | 检查做在哪里 | 残留的窗口 |
|------|------------|-----------|
| 门禁（入队、开跑前检查） | 任务开跑之前 | 从检查到写入之间，任务运行的全部时长 |
| 在串行点外自查代次（如读前、写前各核对一次输入文件戳） | 写入前最后一刻 | 从最后一次核对到 `os.replace` 的毫秒级窗口 |

这类做法能让注定作废的任务早停、压低出错概率，但不能保证正确性。用了它的地方要写明残余风险及为什么可接受；检查挪进安全区后即可去掉。

**前提单调时，门禁本身即闭合**：窗口关不上是因为前提在检查后还可能翻转；前提一旦成立就永不翻转时，门禁就不是缩窗。例：「该版本已不是活跃版本」——版本停了不会复活，新开跑必分配新版本（本仓库离线提交：`clients.get(task).run == run` 即 409，放行后该 run 不可能再变活跃）。要确认两点：翻转在机制上不可能（不是概率低），且版本号不复用（§3.1 规则 1）。

## 5. 按场景选手段

| 场景 | 手段 |
|------|------|
| 写者都在同一进程，单步写很短 | 属主单消费队列 + 写前比对令牌（§2、§3.1 用法一）；路径不跨代复用时写前比对可省 |
| 单个状态点的转换、注册表增删 | 锁内 CAS（§2） |
| 有跨进程写者，或读写要锁定同一代，或路径跨代复用 | 多版本（§3.1 用法二） |
| 耗时任务 | 执行在安全区外，提交在安全区内（§3.2） |
| 删除目录 | rename 到回收区再删，失败按「没删」处理（§2） |
| 前提单调的准入检查 | 门禁即可，写明单调性依据（§4） |
| 靠量级差才触发不到的冲突（如 TTL 天数 ≫ 任务时长） | 写成启动校验，不满足就拒绝启动 |
| 门禁、串行点外自查（前提非单调） | 只用来省算力，写明残余风险（§4） |
| 写错可重跑覆盖、无告警 / DB 等下游副作用、触发频率低 | 可以先不防：写明残余风险，以及结果开始被业务读取时要补防护 |
