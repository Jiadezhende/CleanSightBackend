# 迟到写入与换代冲突：防护设计

- **手段**：「前提检查 + 写」之间不穿插同资源的其他写才算闭合（竞态窗口彻底消除，定义见 §2）。工具有三种：单消费线程队列、锁（含锁内 CAS）、资源的原子操作原语；前两种要求写者在同一进程，跨进程只能用第三种，而且对方的写也必须是原子操作（§2）。
- **要点**：前提检查的常用形态是比对代次令牌；耗时任务不进串行点，执行与提交分离；新一代新建对象而不复用旧对象（§3）。
- **不算闭合**：门禁、在串行点外自查代次，都是在安全区外做检查，最多只能缩小窗口（§4）。
- **现状**：8 项中 5 项已闭合，3 项未闭合，逐项列出残余风险和闭合方案（§5）。

锁清单、队列解耦、生命周期锁等基础设施见 [DESIGN_CONCURRENCY_AND_QUEUES.md](DESIGN_CONCURRENCY_AND_QUEUES.md)。

## 1. 问题：同一资源的写交错，会让另一方的前提失效

对同一资源的写有多种形式：追加、整体替换、删除目录、TTL 回收、注册表增删。它们本质上都是写，下文不再区分。

一次写入是否正确，往往取决于它事先检查过的前提，例如「目录属于当前代」「目录还在」。如果另一次写插在「检查」和「写入」之间，前提就可能已经不成立：

```text
写入方 A                              同一资源上的另一次写 B
  前提检查：目录属于当前代 ✓
                                      B：新一代首写时整域删除 / TTL rmtree
  写入                                ← 前提已不成立：旧数据串进新一代，或把删掉的目录重建成僵尸
```

## 2. 解决方案：闭合竞态窗口的三种工具

- **闭合**：竞态窗口被彻底消除。无论几次写以什么时序交错，同资源的其他写都插不进某次写的「前提检查」和「写入」之间。
- **缩窗**：窗口变小了但仍然存在，极端时序下照样出错（§4）。

要闭合，同一资源上的所有写有两种做法：一是都经过同一个**串行点**（保证写不交错的队列或锁），并在串行点内一起完成前提检查和写入；二是由资源的原子操作一步完成「检查 + 写」。串行点内部和原子操作内部，下文统称**安全区**：只有在安全区内做的检查，才对紧随其后的写有效。

| 工具 | 适用 | 做法 | 本系统实例 | 边界 |
|------|------|------|-----------|------|
| 单消费线程队列 | 同一进程内、单步很短的落盘写（一段 0.26–3 s） | 同一资源的写都提交到同一条 `SerialTaskQueue`，提交顺序就是执行顺序；不能加 worker | recording 的 hls 队列和 detections 队列（追加、新代首写时整域删除、代次表回收都走这两条队列）；离线作业队列（同一 (task, step) 的 read-modify-write 不会并发） | 长任务会堵住队列（§3.2）；跨进程的写者进不来 |
| 锁（含锁内 CAS） | 同一进程内的状态转换、注册表增删 | 比较和变更放在同一个临界区里完成：「当前是 X 才改成 Y」 | `lock_for(task_id)` 事务内的 `stop_run(expected=cq)`；`_wlock` 内的 `remove_if`；`_state_lock` 内的 `to_draining` | 只能管单个状态点，管不了多步流程；跨进程拿不到这把锁 |
| 资源的原子操作原语 | 跨进程、写者之间没法共用串行点 | 由资源一步完成「检查 + 写」；同一资源上与之冲突的写，也必须是原子操作 | 文件系统在目录不存在时原子失败：离线写入传 `create=False`，`open` / `os.replace` 失败后转成 `DirectoryGoneError`，不会把删掉的目录重建出来 | 能检查什么，由原语决定；对方的写也必须是原子的（见下文） |

原子操作原语在本系统中还有两个缺口：

- **能检查的条件不等于真正的前提**：文件系统只能判断「目录在不在」，而真正的前提是「目录属于当前代」。同一路径被新一代重新建出来（ABA）时，它照样放行。这个缺口需要把提交放回串行点才能闭合（§3.2）。DB 的 `UPDATE … WHERE version=?` 能检查版本号，但文件系统没有「按版本号条件换名」这样的原语。
- **对方的写不是原子的**：TTL 用的 `rmtree` 是复合写，分三步：列目录、逐个删除、rmdir。离线写入如果插在中途，最后一步 rmdir 会失败，但前面已经删掉的部分回不来，结果是一个删了一半的目录里留着新文件。
  - 解决办法：把删除改成原子写。先把目录 `rename` 到 `{root}/.trash/`，再对回收区执行 `rmtree`。
  - 这样迟到的写入要么随目录一起进回收区被删掉，要么碰到目录不存在而失败。
  - 回收区的目录名不是数字，TTL 扫描和 `tasks` 列举都不会把它当成 step。
  - Windows 上，如果目录里有打开的句柄，rename 会失败；这一轮跳过，下一轮重试即可。

## 3. 三个设计要点

### 3.1 前提检查的常用形态：比对代次令牌

安全区内的前提检查，最常见的形式是比对**代次令牌**，也就是一个标识「这次写入属于哪一代」的值。

- **令牌的两种形态**：
  - 同一进程内，用对象身份：`cq is current`；
  - 跨进程时对象引用传不过去，改用内容戳：`detections_stamp`，它标识「结果是由哪份输入算出来的」。
- **什么时候需要令牌**：写入的前提由安全区之外的另一份资源决定。换代就是这种情况：「当前是哪一代」记在注册表里，控制面线程执行 `client_manager.set(新 cq)` 时，detections 队列并不知情。所以每个任务都要带上自己的 `cq`，进队列后再和注册表的当前值比对。比对结果有两个用途：
  - 授权删除：只有当前代才能删整个目录。这一条关乎正确性。
  - 丢弃旧代任务：这一条只是为了省开销。
- **什么时候不需要令牌**：写入的前提只取决于同一串行点里的其他写，这时靠顺序就够了。例如 `forget_task` 也走同一条队列，FIFO 保证它排在本代所有写入之后。

### 3.2 耗时任务不进串行点：执行与提交分离

串行点一次只放行一个写。耗时任务放进去，会把同一资源上的其他写全部堵住，吞吐量随之崩掉。所以要把任务拆成两段：

- **耗时的执行放在安全区外**，不受串行约束；
- **提交这一步（比对令牌 + 写入）很短**，放进资源属主的串行点（§2 队列 / 锁）。放不进去的，就用原子操作完成（§2 原子原语），但原子操作能检查的条件有限。

离线目前只拆出了执行这一半：代次比对放在子进程里做（§4），原子操作也只检查了「目录在不在」（§2）。所以「换代 vs 离线结果」还没有闭合（§5）。

### 3.3 新建优于复用：每一代新建对象，做好内存解耦

新一代不要复用上一代的对象再重置状态，而是新建一个对象。迟到的写入手里拿的是旧对象，最多写进旧对象自己，碰不到新一代。

- **内存侧已采用**：每个 run 新建一个不可变的 CQ 对象，不在旧 CQ 上重置字段。CQ 的写门（非 ACTIVE 拒写）用的是免锁读，不是原子的，只负责拦住数据在旧对象里越积越多；真正起隔离作用的是「一代一个对象」。
- **落盘侧仍在复用**：`{step}/hls/` 和 `{step}/inference/` 按 step 复用同一条路径。所以同任务重启时，要靠 §2 的队列加 §3.1 的令牌来处理；离线写入存在的 ABA 窗口，也是由此而来。
- **适用范围**：只针对新旧两代争用同一资源的情况。TTL 回收这类与代次无关的写，不在它的范围内。

## 4. 不算闭合的做法：检查做在安全区外，最多缩小窗口

检查做完之后到写入之前，同一资源上的其他写仍然可能插进来。检查离写入越近，窗口越小，但窗口永远关不上。

| 做法 | 检查做在哪里 | 残留的窗口 |
|------|------------|-----------|
| 门禁（入队、开跑前检查） | 任务开跑之前 | 从检查到写入之间，任务运行的全部时长 |
| 在串行点外自查代次（离线 runner 在读前、读后、写前三次核对 `detections_stamp`） | 子进程内，写入前最后一刻 | 从最后一次核对到 `os.replace` 的毫秒级窗口 |

这类做法能让大部分注定作废的任务早点停下，也能把出错概率压低，但不能拿来保证正确性。凡是用了它的地方，都要写明残余风险，以及为什么可以接受。等检查挪进了安全区，它就可以去掉。

## 5. 系统现状：5 项已闭合，3 项未闭合

| 资源 | 冲突的写 | 手段 | 状态 / 残余风险 | 闭合方案 |
|------|---------|------|----------------|---------|
| run 注册表槽位 | `/api/start` 重启 vs HM 迟到清理 | §2 锁 | 已闭合 | — |
| CQ 内数据 | 拆除 vs decoder 抽帧、结果写回、tick | §3.3 | 已闭合；迟到数据最多落进旧 CQ | — |
| `{step}/inference/`、`{step}/hls/` | 新代首写时整域删除 vs 旧代的段和检测结果 | §2 队列 + §3.1 | 已闭合 | — |
| recording 代次表 | `forget_task` vs 本代写入 | §2 队列（仅靠顺序） | 已闭合 | — |
| `temporal.jsonl` | 同一 (task, step) 的两次离线写入 | §2 队列 + 提交去重 | 已闭合 | — |
| `{step}/inference/` | 新代首写时整域删除 vs 离线结果写入 | §4 点外自查 + §2 原子原语 | **未闭合**：新一代目录里可能混进一份旧分段 | §3.2：「比戳 + 换名」提交到 detections 队列执行 |
| `{step}/` | TTL 回收 vs 离线结果写入 | §2 原子原语（仅离线这一侧是原子的） | **未闭合**：TTL 的 `rmtree` 是复合写，写入插在中途会留下删了一半的 step | §2：TTL 删除改为先 rename 到回收区再删 |
| `{step}/` | TTL 回收 vs recording 拆除后迟到的残段 | 无 | **未闭合**：会出现僵尸 step | §2 的 rename 删除；recording 除认领分支外的写入都改为 `create=False` |

**三个未闭合项目前可以接受，原因如下：**

- 离线结果只供 admin 页可视化，不产生告警，也不写 DB；写错了，重跑一次就会覆盖。
- TTL 只回收 15 天前的数据，而 recording 任务 30 分钟就会超时，所以 recording 那一项目前触发不到。

一旦离线结果开始被业务读取（据此出告警、出报表），就必须按上表的闭合方案处理。
