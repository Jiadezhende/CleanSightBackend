# 迟到写入与换代冲突：防护设计

- **判据**：「前提检查 + 写」必须和同一资源上的其他写互斥，才算闭合（§2）。
- **手段**：互斥靠串行点，串行点有三种来源：单消费线程队列、锁（含锁内 CAS）、文件系统的原生原子失败（§3）。
- **要点**：前提来自串行点之外时才需要代次令牌；长任务在串行点外计算、在点内提交；同任务重启优先按代隔离（§4）。
- **不算闭合**：门禁和在串行点外自查代次只能缩小窗口，提前取消只是为了省资源（§5）。
- **现状**：8 项中 5 项已闭合，3 项未闭合，逐项列出残余风险和闭合方案（§6）。

锁清单、队列解耦、生命周期锁等基础设施见 [DESIGN_CONCURRENCY_AND_QUEUES.md](DESIGN_CONCURRENCY_AND_QUEUES.md)。

## 1. 问题：同一资源的写交错，会让另一方的前提失效

对同一资源的写有多种形式：追加、整体替换、删除目录、TTL 回收、注册表增删。它们本质上都是写，下文不再区分。

一次写入是否正确，往往取决于它事先检查过的前提，例如「目录属于当前代」「目录还在」。如果另一次写插在「检查」和「写入」之间，前提就可能已经不成立：

```text
写入方 A                              同一资源上的另一次写 B
  前提检查：目录属于当前代 ✓
                                      B：新一代首写时整域删除 / TTL rmtree
  写入                                ← 前提已不成立：旧数据串进新一代，或把删掉的目录重建成僵尸
```

## 2. 判据：「前提检查 + 写」能和同资源的其他写互斥，才算闭合

**串行点**：保证同一资源上的两次写不交错的机制。只有当同一资源的所有写都经过同一个串行点，并且前提检查和写入在这个串行点内一起完成时，竞态才算闭合。下文每一种做法都按这条判据归类：满足的在 §3，不满足的在 §5。

## 3. 闭合手段：串行点有三种来源

### 3.1 进程内的短写：单消费线程队列

- **适用场景**：同一进程内、单步很短的写，例如落盘一段只需 0.26–3 s。
- **做法**：同一资源的所有写都提交到同一条 `SerialTaskQueue`，只有一个消费线程，提交顺序就是执行顺序。不要加 worker。
- **本系统实例**：
  - recording 的 hls 队列和 detections 队列：追加、新代首写时整域删除、代次表回收都走这两条队列；
  - 离线作业队列：同一 (task, step) 的 read-modify-write 不会并发。
- **边界**：长任务会堵住整条队列，处理办法见 §4.2。跨进程的写者进不了这个线程。

### 3.2 控制面状态：锁，以及锁内 CAS

- **适用场景**：状态转换、注册表增删。
- **做法**：比较和变更放在同一个临界区里完成，即「当前是 X 才改成 Y」。
- **本系统实例**：
  - `lock_for(task_id)` 事务内的 `stop_run(expected=cq)`，防止 HM 的迟到清理误删被 `/start` 抢先重启的新 run；
  - `_wlock` 内的 `remove_if`（槽位 `is expected` 才删）；
  - `_state_lock` 内的 `to_draining`（是 ACTIVE 才推进）。
- **边界**：只管单个状态点，管不了多步流程。

### 3.3 文件系统：目录不在时写入会原子失败，前提是对方的写也是原子的

- **适用场景**：写者进不了资源属主的串行点（例如子进程），而资源的主要威胁是被删除。
- **做法**：迟到的写者不建目录（`create=False`）。目录不存在时，写 tmp 的 `open` 和换名的 `os.replace` 都会原子失败，存储层把这类失败转成 `DirectoryGoneError`。「目录在不在」的检查和写入由文件系统一步完成，所以这一侧本身是原子的，能保证永远不会写进一个不存在的目录、也不会把删掉的目录重建出来。
- **本系统实例**：离线 runner 写 `temporal.jsonl` 和 `label_probs.npz`。
- **边界**：
  - **对方的写也必须是原子的。** `rmtree` 是复合写：先列目录，再逐个删除，最后 rmdir。如果写入插在中途，文件系统会让最后的 rmdir 失败，但前面已经删掉的部分回不来，结果是一个删了一半的目录里留着新文件。
    - 闭合办法：删除改成先把目录 `rename` 到 `{root}/.trash/`，再对回收区执行 `rmtree`。rename 是原子的，迟到写入要么随目录一起进回收区被删掉，要么碰到目录不存在而失败。回收区的目录名不是数字，TTL 扫描和 `tasks` 列举都不会把它当成 step。
    - Windows 上如果目录里有打开的句柄，rename 会失败；本轮跳过，下轮重试即可。
  - **判据只是「目录在不在」，不等于「目录属于当前代」。** 同一路径被新一代重新建出来（ABA）时它照样放行，这种情况要靠代次令牌（§4.1）。
  - 文件系统没有「按版本号条件换名」这类原语。

## 4. 串行点内的三个设计要点

### 4.1 前提由串行点外的资源决定时，才需要代次令牌

**代次令牌**：标识「这次写入属于哪一代」的值。同一进程内用对象身份（`cq`）；跨进程时对象引用传不过去，用内容戳（`detections_stamp`，标识结果是由哪份输入算出来的）。

- **只靠顺序就够**：写入的前提只取决于同一串行点里的其他写。例如 `forget_task` 也走队列，FIFO 保证它排在本代所有写入之后。
- **需要令牌**：写入的前提由另一份资源决定，而那份资源在这个串行点之外被写。换代就是这种情况：「当前是哪一代」记在注册表里，由 `run_control` 在控制面线程上执行 `client_manager.set(新 cq)`，detections 队列看不到这次写。所以每个任务都带上自己的 `cq`，在队列内部和注册表的当前值比对。令牌有两个用途：
  - **授权删除**：只有 `current is job.cq` 的当前代才能删整个目录。这一条关系到正确性；少了它，拆除之后才执行的残段会把刚写完的数据整个删掉。
  - **丢弃旧代任务**：这一条只是省开销。
- **比对必须放在串行点内**。放在点外就成了 §5 里的「点外自查」，只能缩小窗口。

### 4.2 长任务拆成两段：计算在串行点外，提交在串行点内

长任务不能长时间占住串行点。耗时的计算放在点外；提交这一步（比对令牌 + 写入）很短，放进资源属主的串行点。

离线目前没有这样做：它的比对在子进程里进行（§5），所以「换代 vs 离线结果」还没有闭合（§6）。

### 4.3 同任务重启时，优先按代隔离

同一个 (task, step) 重启之后，新旧两代 run 会写同一份资源。如果每一代有自己独立的容器，旧代的迟到写入就碰不到新代，串台根本不会发生。这一做法只针对同任务重启，TTL 回收这类和代次无关的写不适用。

- **内存侧已采用**：每个 run 对应一个不可变的 CQ 对象。迟到写入持有的是旧 CQ，最多写进旧 CQ 自己。CQ 的写门（非 ACTIVE 拒写）是免锁读、不是原子的，它只负责拦住数据在旧对象里越积越多，隔离本身来自「一代一个对象」。
- **落盘侧未采用**：`{step}/hls/` 和 `{step}/inference/` 按 step 复用同一路径，所以同任务重启要靠 §3.1 的串行点加 §4.1 的令牌来处理。离线写入存在的 ABA 窗口就是由此而来。

## 5. 不算闭合的做法：只缩小窗口，或只节省资源

| 做法 | 作用 | 残留的竞态 |
|------|------|-----------|
| 门禁（入队、开跑前检查） | 大部分注定作废的任务根本不会开跑 | 检查之后插进来的所有写 |
| 在串行点外自查代次（离线 runner 在读前、读后、写前三次核对 `detections_stamp`） | 缩窗：拦住计算期间插进来的换代、追加、删除 | 最后一次核对到 `os.replace` 之间的毫秒级窗口 |
| 提前取消（离线作业服务在 step 进入 live 时 kill 子进程，记为 superseded） | 省资源：不再白白占用 CPU | 不承担正确性；kill 和写入之间同样存在竞态 |

用了这些做法的地方，都必须写明残余风险，以及为什么可以接受。等到同一资源的写全部走同一个串行点，前两项就可以去掉；提前取消是资源上的需求，与此无关，应当保留。

## 6. 系统现状：5 项已闭合，3 项未闭合

| 资源 | 冲突的写 | 手段 | 状态 / 残余风险 | 闭合方案 |
|------|---------|------|----------------|---------|
| run 注册表槽位 | `/api/start` 重启 vs HM 迟到清理 | §3.2 | 已闭合 | — |
| CQ 内数据 | 拆除 vs decoder 抽帧、结果写回、tick | §4.3 | 已闭合；迟到数据最多落进旧 CQ | — |
| `{step}/inference/`、`{step}/hls/` | 新代首写时整域删除 vs 旧代的段和检测结果 | §3.1 + §4.1 | 已闭合 | — |
| recording 代次表 | `forget_task` vs 本代写入 | §3.1（仅靠顺序） | 已闭合 | — |
| `temporal.jsonl` | 同一 (task, step) 的两次离线写入 | §3.1 + 提交去重 | 已闭合 | — |
| `{step}/inference/` | 新代首写时整域删除 vs 离线结果写入 | §5 点外自查 | **未闭合**：新一代目录里可能混进一份旧分段 | §4.2：「比戳 + 换名」提交到 detections 队列执行 |
| `{step}/` | TTL 回收 vs 离线结果写入 | §3.3（仅离线这一侧） | **未闭合**：TTL 的 `rmtree` 是复合写，写入插在中途会留下删了一半的 step | §3.3：TTL 删除改为先 rename 到回收区再删 |
| `{step}/` | TTL 回收 vs recording 拆除后迟到的残段 | 无 | **未闭合**：会出现僵尸 step | §3.3 的 rename 删除；recording 除认领分支外的写入都改为 `create=False` |

**三个未闭合项目前可以接受，原因如下：**

- 离线结果只供 admin 页可视化，不产生告警，也不写 DB；写错了，重跑一次就会覆盖。
- TTL 只回收 15 天前的数据，而 recording 任务 30 分钟就会超时，所以 recording 那一项目前触发不到。

一旦离线结果开始被业务读取（据此出告警、出报表），就必须按上表的闭合方案处理。
