# 迟到写入与换代冲突：防护设计

**问题**：对同一份资源的写入有很多种：追加、整体替换、删除、清理，它们本质上都是写。一次写入是否正确，往往取决于它开始前检查过的前提（「这个目录属于当前代」「这个目录还在」）。只要另一次写入插进了「检查」和「写入」之间，前提就可能已经不成立：旧数据被串进新一代，或者已经删掉的目录又被重建成僵尸。

锁清单、队列解耦、生命周期锁等基础设施，见 [DESIGN_CONCURRENCY_AND_QUEUES.md](DESIGN_CONCURRENCY_AND_QUEUES.md)。

## 结论

1. **只有一种做法能闭合竞态：同一资源的所有写（包括删除、清理）都经过同一个串行点，前提检查和写入在这个串行点内一起完成。**
2. **代次令牌只是被比对的内容，它本身不是解法。** 比对不在串行点内，竞态就还在。
3. **同任务重启时，按代隔离是较好的实践，但它不是通用解法。** 它只管新旧两代 run 之间的串台，管不到 TTL 回收这类与代次无关的写。
4. **门禁、在串行点外自查代次，都只能缩小窗口。** 用了这些，必须写明还剩下什么风险、为什么可以接受，不能写成「已解决」。
   存在性判据（`create=False`）不在此列：它借用了文件系统原生的原子性，只是判据不等于「属于当前代」。
5. **提前取消属于资源需求，与正确性无关。**

## 术语

| 词 | 含义 |
|----|------|
| 写 | 对资源的任何修改：追加、整体替换、删除目录、TTL 回收、注册表增删 |
| 前提检查 | 一次写入依赖的条件判断，例如「当前是哪一代」「目录还在不在」 |
| 串行点 | 保证两次写不会交错的机制：单消费线程、一把锁，或资源自带的原子条件原语 |
| 代次令牌 | 标识「这次写入属于哪一代」的值。同进程内用对象身份（`cq`），跨进程用内容戳（`detections_stamp`） |

## 唯一的正确性机制：同一资源的写经过同一串行点

| 串行点形态 | 适用 | 本系统实例 |
|-----------|------|-----------|
| 单消费线程队列 | 同一进程内、单步很短的写 | recording 的 hls 队列和 detections 队列（追加、首写时整域删除、代次表回收都走队列）；离线作业队列 |
| 锁（含锁内 CAS：当前是 X 才改成 Y） | 控制面的状态转换、注册表增删 | `lock_for(task_id)` 下的 `stop_run(expected=cq)`；`_wlock` 内的 `remove_if`；`_state_lock` 内的 `to_draining` |
| 资源自带的原子条件原语 | 资源本身支持「条件满足才写」，例如 DB 的 `UPDATE … WHERE version=?` | 文件系统的「目录不在就原子失败」：离线写入传 `create=False`，见下文「存在性判据」。文件系统没有「按版本号条件换名」这样的原语 |

**什么时候需要代次令牌，什么时候只靠顺序：**

- **只靠顺序**：写入的前提只取决于同一个串行点里的其他写。例如 `forget_task` 走队列，FIFO 保证它一定排在本代所有写入之后。
- **需要令牌**：写入的前提由**另一份资源**决定，而那份资源是在这个串行点**之外**被写的。换代就是这种情况：「当前是哪一代」记在注册表里，由 `run_control` 在控制面线程上 `client_manager.set(新 cq)` 写入；detections 队列看不到这次写。所以每个任务要带上自己的 `cq`，在队列内部和注册表的当前值比对。比对结果有两个用途：
  - **授权删除**：只有 `current is job.cq` 的当前代才能删整个目录。这一条关系到正确性。
  - **丢弃旧代任务**：这一条只是省开销。

**长任务**：长任务不能长时间占住串行点，所以要拆成两段：**耗时的计算放在串行点外，短小的提交（比对令牌 + 写入）放进串行点内。**

### 存在性判据：借文件系统原生的原子性

迟到的写者不建目录（`create=False`）。写 tmp 用的 `open` 和换名用的 `os.replace`，在目录不存在时会原子地失败，由存储层转成 `DirectoryGoneError`。「目录在不在」的检查和写入，由文件系统在同一步里完成，这一对本身就是原子的。它能保证的是：**永远不会写进一个不存在的目录，也永远不会把删掉的目录重建出来。**

它没覆盖到的两处，问题都不在它自身的原子性：

- **对方的删除不是原子写**：`rmtree` 是复合写，分三步：列目录、逐个删除、最后 rmdir。如果离线写入落在「列目录」和「rmdir」之间，文件系统会正确地让 rmdir 失败（目录非空），但 `rmtree` 前面已经删掉的部分回不来，结果是一个删了一半的目录里留着新文件。
  - **闭合办法：把删除改成原子写。** 先把目录 `rename` 到回收区（`{root}/.trash/`，同一文件系统，非数字目录名，不会被 TTL 扫描或 `tasks` 列举到），再对回收区执行 `rmtree`。`rename` 是原子的，迟到写入只有两种结局：要么落在 rename 之前，随目录一起进回收区被删；要么落在之后，碰到目录不存在而原子失败。
  - Windows 上目录里有打开的句柄时，`rename` 会失败，这一轮 TTL 跳过、下一轮重试即可。
- **判据不等于真正的前提**：它判断的是「目录在不在」，而真正需要的前提是「目录属于当前代」。同一路径被新一代重新建出来（ABA）时，它照样放行。这一项仍然要靠代次令牌。

## 同任务重启：按代隔离是较好的实践

同一个 (task, step) 重启之后，新旧两代 run 会写同一份资源。如果每一代有自己独立的容器，旧代迟到的写入就碰不到新代，串台根本不会发生。这一节只针对这个场景。

- **内存侧已采用**：每个 run 对应一个不可变的 CQ 对象。迟到的写入拿的是旧 CQ，最多写进旧 CQ 本身。CQ 的写门（非 ACTIVE 拒写）用的是免锁读，不是原子的，它只负责拦住旧对象里继续堆积数据；真正起隔离作用的是「一代一个对象」。
- **落盘侧未采用**：`{step}/hls/` 和 `{step}/inference/` 按 step 复用同一条路径，同任务重启要靠「串行点 + 代次令牌」处理。recording 已经闭合；离线只做到缩窗，「换代 vs 离线结果」的 ABA 窗口就是这么来的。
- **不适用**：TTL 回收这类写与代次无关，不管哪一代都整个删掉，只能靠串行点。

## 只能缩窗的做法（不是解法）

| 做法 | 缩掉了什么 | 残留的竞态 |
|------|-----------|-----------|
| 门禁（入队 / 开跑前检查） | 大部分注定作废的任务不会开跑 | 检查之后插进来的所有写 |
| 在串行点外自查代次（离线 runner 在读前、读后、写前三次核对 `detections_stamp`） | 计算期间插进来的换代、追加、删除 | 最后一次核对到 `os.replace` 之间的毫秒级窗口 |

这两种做法之所以存在，都是因为同一资源的写没有全部走同一个串行点。一旦走了，这两种都可以去掉。

## 需求，不属于正确性：提前取消

离线作业服务在发现对应 step 变成 live 时，会 kill 子进程并把作业记为 superseded，目的是不白白占用 CPU。正确性不能依赖它：kill 和写入之间同样有竞态。

## 系统现状

| 资源 | 互相冲突的写 | 是否闭合 | 机制 | 残余风险 | 闭合方案 |
|------|------------|---------|------|---------|---------|
| run 注册表槽位 | `/api/start` 重启 vs HM 迟到清理 | 已闭合 | 锁：`lock_for` 事务内的 `stop_run(expected)` + `remove_if` | 无 | — |
| CQ 内的数据 | 拆除 vs decoder 抽帧 / 结果写回 / tick | 已闭合 | 按代隔离（一个 run 一个 CQ） | 迟到的数据最多落进旧 CQ | — |
| `{step}/inference/`、`{step}/hls/` | 新代首写时整域删除 vs 旧代的段 / 检测结果 | 已闭合 | 同一条队列 + 在队列内比对 `cq` 令牌；删除只由当前代执行 | 无 | — |
| recording 代次表 | `forget_task` vs 本代写入 | 已闭合 | 队列顺序 | 无 | — |
| `temporal.jsonl` | 同一 (task, step) 的两次离线写入 | 已闭合 | 离线作业队列 + 提交时去重 | 无 | — |
| `{step}/inference/` | 新代首写时整域删除 vs 离线结果写入 | **未闭合，只缩窗** | 在串行点外自查戳 | 新一代目录里可能混进一份旧分段 | 计算留在子进程；「比戳 + 换名」提交到 detections 队列执行 |
| `{step}/` | TTL 回收 vs 离线结果写入 | **未闭合** | 存在性判据（离线写入这一侧是原子的） | TTL 的 `rmtree` 是复合写：离线写入插在中途时会留下删了一半的 step | 把 TTL 删除改成原子写：先 `rename` 到 `{root}/.trash/`，再执行 `rmtree`。配合现有的 `create=False` 即可闭合 |
| `{step}/` | TTL 回收 vs recording 迟到残段 | **未闭合，无防护** | — | 僵尸 step | 同上一行的 rename 删除；另外 recording 除认领分支（本代首写）外的写入改为 `create=False` |

**三个未闭合项目前可以接受的理由：**
- 离线结果只给 admin 做可视化，不出告警、不写 DB；写错了，重跑一次就能覆盖。
- TTL 只回收 15 天前的数据，而 recording 任务 30 分钟就超时，所以 recording 那一项现在触发不到。

一旦离线结果开始被业务读取（据此出告警、出报表），就必须按上表的「闭合方案」处理。
