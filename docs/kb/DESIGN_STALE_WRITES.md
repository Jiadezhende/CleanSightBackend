# 迟到写入与换代冲突：防护设计

- **判据**：「前提检查 + 写」之间不穿插同资源的其他写才算闭合（§2）。
- **工具**：单消费线程队列、锁（含锁内 CAS）、资源的原子操作原语。前两种要求写者在同一进程；跨进程只能用第三种，而且对方的写也必须是原子的（§2）。
- **要点**（§3）：
  - 代次令牌有两种用法：各代共用资源时写前比对；各代各写一个版本，由读侧按版本号选（多版本 / MVCC）。有跨进程写者或路径跨代复用时，优先用多版本。
  - 耗时任务执行与提交分离。
  - 每一代新建对象，不复用。
- **不算闭合**：门禁、在串行点外自查代次，都是在安全区外做检查，最多只能缩小窗口（§4）。
- **怎么选**：按场景对应工具（§5）；写错可重跑覆盖、无下游副作用的产物可以先不防。

锁清单、队列解耦、生命周期锁等基础设施见 [DESIGN_CONCURRENCY_AND_QUEUES.md](DESIGN_CONCURRENCY_AND_QUEUES.md)。

## 1. 问题：同一资源的写交错，会让另一方的前提失效

对同一资源的写有多种形式：追加、整体替换、删除目录、TTL 回收、注册表增删。它们本质上都是写，下文不再区分。

一次写入是否正确，往往取决于它事先检查过的前提，例如「目录属于当前代」「目录还在」。如果另一次写插在「检查」和「写入」之间，前提就可能已经不成立：

```text
写入方 A                              同一资源上的另一次写 B
  前提检查：目录属于当前代 ✓
                                      B：新一代首写时整域删除 / TTL rmtree
  写入                                ← 前提已不成立：旧数据串进新一代，或把删掉的目录重建成僵尸
```

## 2. 解决方案：闭合竞态窗口的三种工具

- **闭合**：竞态窗口被彻底消除。无论几次写以什么时序交错，同资源的其他写都插不进某次写的「前提检查」和「写入」之间。
- **缩窗**：窗口变小了但仍然存在，极端时序下照样出错（§4）。

要闭合，同一资源上的所有写有两种做法：一是都经过同一个**串行点**（保证写不交错的队列或锁），并在串行点内一起完成前提检查和写入；二是由资源的原子操作一步完成「检查 + 写」。串行点内部和原子操作内部，下文统称**安全区**：只有在安全区内做的检查，才对紧随其后的写有效。

| 工具 | 适用 | 做法 | 例 | 边界 |
|------|------|------|----|------|
| 单消费线程队列 | 同一进程内、单步很短的落盘写 | 同一资源的写都提交到同一条 `SerialTaskQueue`，提交顺序就是执行顺序；不能加 worker | recording 的 hls 队列与 detections 队列（追加、新代首写时整域删除、代次表回收都走各自的队列） | 长任务会堵住队列（§3.2）；跨进程的写者进不来 |
| 锁（含锁内 CAS） | 同一进程内的状态转换、注册表增删 | 比较和变更放在同一个临界区里完成：「当前是 X 才改成 Y」 | `lock_for(task_id)` 内的 `stop_run(expected=cq)`；`_wlock` 内的 `remove_if` | 只能管单个状态点，管不了多步流程；跨进程拿不到这把锁 |
| 资源的原子操作原语 | 跨进程、写者之间没法共用串行点 | 由资源一步完成「检查 + 写」；同一资源上与之冲突的写，也必须是原子操作 | 本仓库暂未落地。形态如：迟到写者写入时不建目录，目录不在则 `open` / `os.replace` 由文件系统原子失败，不把删掉的目录重建出来 | 能检查什么由原语决定；对方的写也必须是原子的（见下） |

原子原语的两个局限：

- **能检查的条件不等于真正的前提**：文件系统只能判断「目录在不在」，而真正的前提往往是「目录属于某一代」。同一路径被新一代重新建出来（ABA）时，它照样放行。解法是让路径不跨代复用（§3.1 多版本），或把提交放回属主串行点（§3.2）。DB 的 `UPDATE … WHERE version=?` 能检查版本号，文件系统没有「按版本号条件换名」这样的原语。
- **对方的写不是原子的**：`rmtree` 是复合写，分三步：列目录、逐个删除、rmdir。
  - 写入插在中途：最后一步 rmdir 会失败，但前面已经删掉的部分回不来，结果是一个删了一半的目录里留着新文件。
  - 删除自己半途失败（Windows 上有文件被打开时会删不动）：目录里已经少了一部分。调用方如果把「删过了」记下来接着写，新旧数据就混在同一目录里。
  - 解决办法：把删除改成原子写。先把目录 `rename` 到 `{root}/.trash/`，再对回收区执行 `rmtree`。迟到的写入要么随目录一起进回收区，要么碰到目录不存在而失败；rename 失败则目录原样未动，调用方必须把它当成「没删」处理。
  - 回收区的目录名不是数字，按数字目录名扫描 step 的逻辑都不会把它当成 step。rmtree 失败的留在回收区，下一轮再清。

## 3. 三个设计要点

### 3.1 代次令牌：写前比对，或多版本（MVCC）

**代次令牌**是标识「这次写属于哪一代」的值。它有两种用法，本质相同，都是用令牌把不同代的写区分开；差别在于区分发生在哪一侧：

| 维度 | 写前比对 | 多版本（MVCC） |
|------|---------|---------------|
| 资源形态 | 各代共用一份（盘上同一路径） | 一代一个版本（盘上一代一个目录） |
| 令牌在哪里比 | 写者在安全区内比 | 读者按版本号选；写者只写自己那一版 |
| 换代动作 | 删除旧代，再写新代 | 新版本提交即生效，旧版本异步回收 |
| 迟到写入 | 必须进属主串行点比对，否则只能缩窗 | 写进旧版本，读者看不到 |
| 适用 | 写者都在同一进程、都走属主串行点 | 有跨进程写者、读写要锁定同一代，或路径跨代复用导致 ABA |

**令牌的形态**：

- 进程内：对象身份，`cq is current`。
- 跨进程 / 落盘：持久的版本号。内容戳（如 `(inode, size, mtime)`）只能说明「变没变」，说明不了「属于哪一代」，不能当令牌用。

#### 用法一：写前比对

适用于写入的前提由安全区之外的另一份资源决定的情况。换代就是这种情况：「当前是哪一代」记在注册表里，控制面线程执行 `client_manager.set(新 cq)` 时，属主队列并不知情。所以每个任务都要带上自己的 `cq`，进队列后再和注册表的当前值比对。比对结果有两个用途：

- 授权删除：只有当前代才能删整个目录。这一条关乎正确性。
- 丢弃旧代任务：这一条只是为了省开销。

#### 用法二：多版本（MVCC）

各代写各自的版本目录，彼此在盘上不相交，「哪一代生效」由读侧决定。规则：

1. **版本号在同一资源内严格单调、永不复用。** 在同资源的串行点内按 `max(当前时间, 已有最大 + 1)` 分配，再加一段随机后缀；排序只看时间前缀，身份比较用整串。不直接用墙钟：时钟回拨会让新版本不可见，还会被当成旧版本回收。
2. **一代只分配一次版本号，各域共用。** 跨域配对（如录像与检测结果）比较版本号。
3. **提交是原子的。** 首份产物写进 `.{版本}.tmp/`，写完后 rename 成 `{版本}/`；读者跳过点号开头的目录。空版本一旦可见，就会遮住上一代。
4. **只有属主能建版本。** 其余写者只写已存在的版本，不建目录（`create=False`）。
5. **读者取最大的已提交版本，只解析一次。** 解析结果是一个句柄（task, step, 版本），此后整次读写都用这个句柄；读写接口只收句柄，不提供「默认取最新」。跨多次请求的读（如 HLS 回放：先取清单、再多次取段）把版本号带进 URL。
6. **输入冻结要显式标记。** 属主在一代最后一次写之后落封口标记（`SEALED`）；下游消费只接受已封口的版本。进程重启时，所有未封口的版本都已经没有写者，统一补封。
7. **回收（vacuum）只回收非最新的版本。** 条件是被后继版本取代超过宽限期，宽限期要大于最长的锁定读者（如离线作业超时）。版本号只增，「非最新」一旦成立就不会翻转，回收判断无需和写侧互斥。
8. **删除按 §2 的原子删除做**：先 rename 到回收区，失败按「没删」处理。
9. **一个文件只有一个写者。** 多个 producer 各写各的文件，读侧合并；不在文件上做跨进程的「读回 → 合并 → 写回」。

与数据库 MVCC 的对应：

```text
数据库 MVCC                          落盘多版本
版本号来自单调计数器（txid）         max(当前时间, 已有最大 + 1) + 随机后缀
读者选最新的已提交版本               选最大的 {版本}/；.tmp 即未提交
提交原子                             rename .{版本}.tmp → {版本}
快照读                               解析一次得到句柄，整次读写锁定同一版本
vacuum 不回收仍有读者的版本          只回收非最新且被取代超过宽限期的版本
```

与数据库有一处不同：数据库的读者看「不晚于自己快照的最新版本」，这里的读者在解析那一刻看全局最新，之后锁定。

#### 什么时候不需要令牌

写入的前提只取决于同一串行点里的其他写时，靠顺序就够了。例如 recording 的 `forget_task` 也走同一条队列，FIFO 保证它排在本代所有写入之后。

### 3.2 耗时任务不进串行点：执行与提交分离

串行点一次只放行一个写。耗时任务放进去，会把同一资源上的其他写全部堵住，吞吐量随之崩掉。所以要把任务拆成两段：

- **耗时的执行放在安全区外**，不受串行约束；
- **提交这一步（比对令牌 + 写入）很短**，放进资源属主的串行点（§2 队列 / 锁）。放不进去的，就用原子操作完成（§2 原子原语），但原子操作能检查的条件有限。

采用多版本时，提交不必进串行点：写者只写自己锁定的那个版本，和其他代在盘上不相交（§3.1）。

### 3.3 新建优于复用：每一代新建对象

新一代不要复用上一代的对象再重置状态，而是新建一个对象。迟到的写入手里拿的是旧对象，最多写进旧对象自己，碰不到新一代。

- **内存侧**：每个 run 新建一个 CQ 对象，不在旧 CQ 上重置字段。CQ 的写门（非 ACTIVE 拒写）用的是免锁读，不是原子的，只负责拦住数据在旧对象里越积越多；真正起隔离作用的是「一代一个对象」。
- **落盘侧**：同一原则的落盘形态就是 §3.1 的多版本，一代一个版本目录。复用同一路径的，只能靠写前比对加属主串行点兜住，跨进程写者还会留下 ABA 窗口。
- **适用范围**：只针对新旧两代争用同一资源的情况。TTL 回收这类与代次无关的写，不在它的范围内。

## 4. 不算闭合的做法：检查做在安全区外，最多缩小窗口

检查做完之后到写入之前，同一资源上的其他写仍然可能插进来。检查离写入越近，窗口越小，但窗口永远关不上。

| 做法 | 检查做在哪里 | 残留的窗口 |
|------|------------|-----------|
| 门禁（入队、开跑前检查） | 任务开跑之前 | 从检查到写入之间，任务运行的全部时长 |
| 在串行点外自查代次（如读前、写前各核对一次输入文件戳） | 写入前最后一刻 | 从最后一次核对到 `os.replace` 的毫秒级窗口 |

这类做法能让大部分注定作废的任务早点停下，也能把出错概率压低，但不能拿来保证正确性。凡是用了它的地方，都要写明残余风险，以及为什么可以接受。等检查挪进了安全区，它就可以去掉。

## 5. 怎么选

| 场景 | 手段 |
|------|------|
| 写者都在同一进程，单步写很短 | 属主单消费队列 + 写前比对令牌（§2、§3.1 用法一） |
| 单个状态点的转换、注册表增删 | 锁内 CAS（§2） |
| 有跨进程写者，或读写要锁定同一代，或路径跨代复用 | 多版本（§3.1 用法二） |
| 耗时任务 | 执行在安全区外，提交在安全区内（§3.2） |
| 删除目录 | rename 到回收区再删，失败按「没删」处理（§2） |
| 靠量级差才触发不到的冲突（如 TTL 天数 ≫ 任务时长） | 写成启动校验，不满足就拒绝启动 |
| 门禁、串行点外自查 | 只用来省算力，写明残余风险（§4） |
| 写错可重跑覆盖、不产生告警 / DB 等下游副作用、触发频率低 | 可以先不防：写明残余风险，以及结果开始被业务读取时要补上防护 |
